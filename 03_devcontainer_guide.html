Dev Container：Nav2 の開発の環境を container でそろえる

Local Installation の章では、Nav2 をソースからビルドするために、WSL の Ubuntu に rosdep で依存を入れ、colcon でビルドした。1 人で試すならこれで足りる。けれども、製品をチームで開発するようになると、困ったことが起きる。ある人の PC ではビルドが通るのに、別の人の PC では通らない。調べると、入っている依存の版が少しずつ違う。新しく加わった人は、環境をそろえるだけで 1 日が終わる。

このページでは、その解決の 1 つである dev container（開発の環境を丸ごと入れた Docker の container）を使って、Nav2 をビルドする。Nav2 のリポジトリには、dev container の設定が入っている。それを使うと、Nav2 の CI（変更のたびに自動でビルドとテストを行う仕組み）とほぼ同じ環境が、手元に出来上がる。

このページについて

  • Nav2 の公式の文書の Dev Containers と Dev Container Guide（jazzy 版の原稿、コミット b22554c）を基に、日本語で説明し直したもの。逐語の翻訳ではない。Docker の導入は Docker の公式の文書、VS Code の操作は VS Code の公式の文書（出典に列挙）を使った。出典とライセンスはページの末尾にある。
  • ROS 2 Jazzy と Ubuntu 24.04（Windows の WSL2 を含む）を前提にする。Local Installation の章の 4-1 節で、~/nav2_ws/src/navigation2 にソースを取得してあることを前提にする。
  • このページは飛ばしてもよい。後の章は、Local Installation の章の環境（WSL に直接入れた環境）で進める。チームで環境をそろえる方法を知りたいとき、Nav2 の CI と同じ環境でビルドを確かめたいときに読む。
  • 期待する結果の出どころ: 3-1 節の systemd の確かめ方だけは作成時の環境で確かめた。それ以外の表示は、どれも想定（Docker と VS Code の公式の文書、Nav2 のリポジトリの jazzy ブランチの設定のファイルから）。設定のファイルは、2026-11-17 のコミット c7046550 のものを読んだ。
  • 4 節の container の作成では、Nav2 の全体をビルドする。Local Installation の章の 4-4 節と同じく、1 時間を超えることがある。

0. 学習目標と完了条件

このページを終えると、次のことができる。

  1. dev container が何で、なぜ使うのかを、WSL に直接入れる方法と比べて説明できる。
  2. Nav2 の dev container を VS Code で開き、その中で Nav2 をビルドして、ROS 2 のコマンドを使える。
  3. dev container を作り直すと何が消え、何が残るのかを説明できる。

完了条件は、5 節の ros2 pkg prefix nav2_bringup が、container の中でビルドした場所（/opt/overlay_ws/install/nav2_bringup）を指すこと。

1. 全体像

このページでは、Docker の言葉を 3 つ使う。

  • image: container の元になる、ファイルとプログラムの一式。OS の一部・ROS 2・Nav2 の依存などが入っている。作り方は Dockerfile（image の作り方を順に書いたファイル）に書く。
  • container: image を元に動かす、ほかから切り離された環境。中で動くプログラムからは、自分だけの Ubuntu があるように見える。この章の container は Docker の container で、Quickstart の章の 6 節で見た、Nav2 の node をまとめて入れる container（component container）とは別のものである。
  • volume: container の外に置かれ、container を消しても残る保存場所。

WSL を使う PC では、次の図のような形になる。画面は Windows の VS Code に出るが、ファイルを読み書きしてプログラムを動かすのは WSL と container の中である。

ソースのフォルダは、WSL と container の両方から同じものが見える（bind mount。WSL のフォルダを、container の中の別の場所に見せる仕組み）。どちらで直しても、同じファイルが変わる。一方、ビルドの結果（build・install）は container の側の volume に置かれ、Local Installation の章の ~/nav2_ws/install とは別になる。

2. dev container とは

公式の原稿は、dev container を「プロジェクトの開発に要る道具と依存をすべて入れた Docker の container」と説明している。Local Installation の章の方法と比べると、違いは次のとおりである。

比べる点WSL に直接入れる（Local Installation）dev container
依存を入れる場所WSL の Ubuntu（/opt/ros/jazzy など）container の中。WSL には Docker だけを入れる
環境の決め方人が手順を実行した結果で決まるDockerfile と devcontainer.json に書かれた内容で決まる
ほかの人との違い入れた時期や順番で、版が少しずつずれうる同じ設定から作るので、そろいやすい
ROS 2 の版を混ぜない読み込む環境（source）で使い分けるプロジェクトごとに別の container にする
最初の準備の重さ軽いDocker の導入と、image の作成が要る

dev container の設定は、プロジェクトの直下の .devcontainer フォルダの devcontainer.json に書く。この形は Development Containers という公開の仕様で決まっていて、VS Code のほか、ほかの道具やクラウドの開発環境（GitHub Codespaces など）でも使える。このページでは、公式の原稿と同じく VS Code を使う。

VS Code でプロジェクトのフォルダを開くと、VS Code が .devcontainer を見つけ、container で開き直すかを尋ねる。開き直すと、VS Code は container を作って起動し、プロジェクトのフォルダを container の中に見せ、自分自身の一部（VS Code Server）を container の中で動かす。画面は手元の VS Code のままで、ファイルの編集・ターミナル・ビルドは container の中で行われる。

3. 準備：Docker と VS Code

公式の原稿は、前提として Docker Engine（container を動かす本体）・VS Code・VS Code の Dev Containers の拡張機能を挙げている。WSL を使う PC では、Docker Engine を WSL の Ubuntu に入れ、Windows の VS Code から WSL の拡張機能を通して使う。VS Code の公式の文書は、この形を Docker の別の使い方の 1 つとして挙げている（Windows に Docker Desktop を入れる形もあるが、このサイトでは扱わない）。Ubuntu を直接入れた PC では、3-1 節の systemd の確かめと、3-4 節の WSL の拡張機能を飛ばす（3-3 節のグループの変更は、WSL を止める代わりにログインし直して効かせる）。

3-1. systemd が動いているかを確かめる

Docker Engine は、裏で動き続けるプログラム（dockerd）として動く。Ubuntu では、これを systemd（Ubuntu で、裏で動くプログラムを起動・管理する仕組み）が起動する。VS Code の公式の文書は、WSL で systemd が動いていないと dockerd が自動で起動しないと注意している。

# T1
ps -p 1 -o comm=

# T1 は「1 つめのターミナル（WSL の Ubuntu）で実行する」という印で、# から後はコメントなので打たなくてよい（この印は、この後のコマンドの箱でも同じ）。

期待する結果

systemd

最初に起動したプログラム（番号 1）の名前を表示している。systemd と出れば、systemd が動いている。作成時の環境（環境構築の章の手順で入れた Ubuntu 24.04）では、こう出た。init など別の名前が出たら、VS Code の公式の文書が案内する Microsoft の記事（出典に列挙）に従って、WSL の systemd を有効にする。

3-2. Docker Engine を入れる

Docker の公式の文書の、Docker の apt のリポジトリから入れる手順に従う。環境構築の章の 4 節で ROS 2 のリポジトリを足したのと同じく、apt の取得元を足してから入れる。

先に、Docker の公式のパッケージとぶつかりうるもの（Ubuntu が用意している非公式の Docker の docker.io など、Docker が自分のパッケージにまとめて入れる containerd・runc）を取り除く。Docker の公式の文書は、次の形で一度に取り除く手順を挙げている。同じ文書によると、どれも入っていないと apt が報告することもある。

# T1
sudo apt remove $(dpkg --get-selections docker.io docker-compose docker-compose-v2 docker-doc docker-buildx podman-docker containerd runc | cut -f1)

期待する結果

dpkg: no packages found matching docker.io
（中略）
0 upgraded, 0 newly installed, 0 to remove and … not upgraded.

想定（どれも入っていない場合。dpkg と apt の表示の形から）。no packages found matching は、その名前のパッケージが入っていないという知らせで、失敗ではない。0 to remove なら、何も取り除かれていない。入っていたものがあれば、その名前が取り除くものとして並び、続けるかを聞かれる。

次に、Docker の apt のリポジトリを足す。

  • sudo curl … -o /etc/apt/keyrings/docker.asc: Docker の鍵（apt が、取得したパッケージが Docker の作ったものかを確かめるための公開鍵）を保存する。
  • sudo tee … <<EOF から EOF まで: apt の取得元のファイルを書く。tee の後の 6 行がファイルの中身で、$(…) の部分は、Ubuntu の版の名前（Ubuntu 24.04 では noble）と CPU の種類（多くの PC では amd64）に置き換わる。最後の EOF の行までを、まとめて貼り付けて実行する。
# T1
sudo apt update

sudo apt install ca-certificates curl

sudo install -m 0755 -d /etc/apt/keyrings

sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc

sudo chmod a+r /etc/apt/keyrings/docker.asc

sudo tee /etc/apt/sources.list.d/docker.sources <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF

sudo apt update

期待する結果

（前略）
Get:… https://download.docker.com/linux/ubuntu noble InRelease
（中略）
Reading package lists... Done

想定（apt の表示の形から）。最後の sudo apt update の表示に、download.docker.com の行があれば、取得元が足されている。Get は Hit のこともある。鍵が無いという意味の NO_PUBKEY などのエラーが出たら、鍵を保存した行から順にやり直す。

取得元を足したら、Docker のパッケージを入れる。

# T1
sudo apt install docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin

sudo systemctl status docker

期待する結果

● docker.service - Docker Application Container Engine
     Loaded: loaded (/usr/lib/systemd/system/docker.service; enabled; preset: enabled)
     Active: active (running) since …
（後略）

想定（Docker と systemd の表示の形から）。Active: active (running) と出れば、dockerd が動いている。表示が続いて入力に戻らないときは、q で抜ける。active でなければ、Docker の公式の文書のとおり sudo systemctl start docker で起動する。

docker-buildx-plugin は image を作る道具で、4 節で dev container の image を作るときに使われる。

最後に、試しの image を動かして、Docker が使えることを確かめる。

# T1
sudo docker run hello-world

期待する結果

Unable to find image 'hello-world:latest' locally
（中略）
Hello from Docker!
This message shows that your installation appears to be working correctly.
（後略）

想定（Docker の公式の文書の説明から）。手元に無い image hello-world をインターネットの image の置き場所（registry）から取得し、container として動かして、メッセージを表示して終わる。Hello from Docker! が出ればよい。

3-3. sudo を付けずに docker を使えるようにする

VS Code の公式の文書は、Linux で dev container を使う準備として、ユーザーを docker グループに入れて、sudo を付けずに docker を使えるようにする手順を挙げている。Docker の公式の文書も、ユーザーを docker グループに入れる方法を挙げている。同じ文書によると、apt で Docker を入れると、Linux のディストリビューションによってはこのグループが自動で作られる（作られていなければ、文書のとおり先に sudo groupadd docker で作る）。

注意: Docker の公式の文書は、docker グループは root（管理者）と同等の権限を与える、と警告している。この警告から推すと、docker を使えるユーザーは、container を通して WSL の中のどのファイルでも書き換えられると考えておくのが安全である。自分だけが使う開発用の PC で行う。

# T1
sudo usermod -aG docker $USER

グループの変更は、ログインし直すまで効かない。WSL では、Ubuntu のターミナルと VS Code をすべて閉じてから、Windows の PowerShell で wsl --shutdown（環境構築の章の 2 節）を実行して WSL を止め、Ubuntu のターミナルを開き直すのが確実である（VS Code の WSL の側も、新しいグループで起動し直させるため）。Ubuntu を直接入れた PC では、Docker の公式の文書のとおり、ログアウトしてログインし直す。開き直したら、sudo を付けずに確かめる。

# T1
docker run hello-world

期待する結果

Hello from Docker!
This message shows that your installation appears to be working correctly.
（後略）

想定（Docker の公式の文書から）。image はすでに手元にあるので、取得の行は出ない。permission denied と出たら、グループの変更がまだ効いていない。WSL では WSL を止めて開き直すところから、Ubuntu を直接入れた PC ではログインし直すところから、やり直す。

3-4. VS Code と拡張機能を入れる

VS Code がまだ無ければ、VS Code のサイトから入れる。VS Code の公式の文書は、WSL を使う PC では、WSL の中ではなく Windows の側に入れるよう書いている。入れる途中の「追加タスクの選択」（Select Additional Tasks）で、PATH への追加（Add to PATH）に印を付ける。これを付けないと、4 節で WSL のターミナルから code のコマンドを使えない。入れた後は、開いていた WSL のターミナルを開き直す。

次に、Windows の VS Code に、次の 2 つの拡張機能を入れる（どちらも Microsoft のもの）。拡張機能の画面（Ctrl+Shift+X）で名前を検索して入れる。

  • WSL（ID: ms-vscode-remote.remote-wsl）: Windows の VS Code から、WSL の中のフォルダを開く。
  • Dev Containers（ID: ms-vscode-remote.remote-containers）: dev container を作って開く。

4. container で開く

Local Installation の章で取得したソースのフォルダを、WSL のターミナルから VS Code で開く。

# T1
cd ~/nav2_ws/src/navigation2

code .

code . は、今いるフォルダを VS Code で開く。WSL のターミナルから実行すると、Windows の VS Code が WSL の拡張機能を通して開く（初回は、WSL の中に VS Code Server が入る）。左下の表示に WSL: Ubuntu-24.04 のような WSL の名前が出ていればよい。

開く前に確かめる: container で開くと、設定のファイルに書かれたコマンドが自動で実行され、拡張機能が自動で入る。Nav2 の設定では、AI がコードを補う拡張機能（GitHub Copilot）が入ることと、ROS 2 の通信の実装の 1 つ（RTI Connext DDS）のライセンスに自動で同意する設定があることを、先に知っておく。詳しくは 8 節で、入れたくない拡張機能を外す方法と、ライセンスの無償の範囲を説明している。会社の PC で試すなら、8 節を先に読む。

フォルダに .devcontainer があるので、右下に、container で開き直すかを尋ねる通知が出ることがある。通知の Reopen in Container を押す。通知が出ないときは、コマンドパレット（Ctrl+Shift+P）で Dev Containers: Reopen in Container を選ぶ（公式の原稿の Remote-Containers: … は、この拡張機能の古い名前である）。このフォルダの作者を信頼するかを尋ねられたら、上の確かめを済ませてから答える。

初回は、次のことが順に起きる。公式の原稿は「待つ間に、足を伸ばしたりコーヒーを入れたりしてよい」と書いている。

  1. image を作る: Nav2 の Dockerfile は、image をいくつかのstage（段。前の stage の image に足していく、作り方の区切り）に分けて書いている。devcontainer.json は、そのうち開発用の dever の stage を指しているので、そこまでを作る。元になる ros:jazzy の image（ROS 2 Jazzy の基本の部分だけが入ったもの）を取得し、その上に、ビルドの道具・Nav2 の依存（rosdep で入れる）・TurtleBot のシミュレーションの部品（/opt/underlay_ws にビルドする）・開発の道具（gdb など）を重ねる。時間を縮めるため、Nav2 の CI が image の置き場所に公開している image（ghcr.io/ros-navigation/navigation2:jazzy）を、作り方が同じ部分の控えとして使う。
  2. container を起動し、Nav2 をビルドする: devcontainer.json の onCreateCommand が、次の 3 で見るスクリプトを呼んで、container の中の /opt/overlay_ws（Local Installation の章の ~/nav2_ws に当たる workspace）で、Nav2 の全体を colcon でビルドする。同時に、VS Code の拡張機能が container の中に入る（8 節）。
  3. 仕上げ: updateContentCommand と postCreateCommand が動く。前者のスクリプトは、ビルドが終わっていないパッケージ・失敗したパッケージ・ソースが変わったパッケージと、それらに依存するパッケージを選んでビルドする（2 の全体のビルドも、最初はすべてが「終わっていない」ので、このスクリプトで行われる）。公式の原稿は、この 2 つは container を起動するたびに動くと書いているが、Dev Container の仕様では、updateContentCommand と postCreateCommand は container を作るときに動くもので、起動のたびに動くのは別の項目（postStartCommand）である。どちらの振る舞いになるかは確かめていない。

右下の Starting Dev Container (show log) の通知を押すと、今どこまで進んだかのログが見られる。公式の原稿によると、後からログを見るときは、コマンドパレットに Dev Containers: Show Log と打つと、ログを見るためのコマンドが並ぶ。

期待する結果

想定（VS Code の公式の文書と Nav2 の設定のファイルから）。待った後、VS Code の左下の表示が Dev Container: Nav2 のような container の名前に変わり、左のファイルの一覧に Nav2 のソースが並ぶ。ログの最後のほうに、colcon のビルドの Summary: … packages finished が出ていれば、ビルドが終わっている。

メモリの少ない PC では: 2 のビルドは、Local Installation の章の 4-4 節と同じく、Nav2 の全体を、既定の並べ方でビルドする（並べる数を絞る指定は無い）。その章の 4-5 節で見たとおり、メモリが足りないと PC ごと固まることがある。固まったら、PC を再起動するか、Windows の PowerShell で wsl --shutdown を実行して WSL を止め、WSL のターミナルから 4 節の初めのとおりに開き直す。それでもビルドが続かないときは、VS Code のターミナル（Ctrl+Shift+`。container の中の bash が開く。この後のコマンドの箱では、このターミナルを # T2 で表す）で、3 で見たスクリプトを自分で実行する。

# T2
cd /opt/overlay_ws/src/navigation2

.devcontainer/update-content-command.sh

スクリプトの中身から読むと、3 で見たとおりにパッケージを選んで、続きからビルドする。ただし、並べる数を絞らない同じ形でビルドするので、再び固まることがある。ここに書いた戻り方は、どれも確かめていない想定である（container を作る途中で止まった後に、VS Code が container の中のターミナルを開ける状態になるかも、確かめていない）。

5. container の中で使う

VS Code のターミナル（Ctrl+Shift+`）を開くと、container の中の bash が開く。ここから先の # T2 のコマンドは、このターミナルで実行する（4 節の終わりと同じ）。開いた直後の場所は、ソースのフォルダ /opt/overlay_ws/src/navigation2 である。

この container では、ターミナルを開くと、TurtleBot のシミュレーションの部品を入れた underlay（/opt/underlay_ws）が自動で読み込まれる。Nav2 をビルドした overlay（/opt/overlay_ws）は自動では読み込まれないので、Local Installation の章の 5 節と同じく、自分で読み込む。

# T2
cd /opt/overlay_ws

source install/setup.bash

ros2 pkg prefix nav2_bringup

期待する結果

/opt/overlay_ws/install/nav2_bringup

想定（Nav2 の設定のファイルから）。container の中でビルドした Nav2 が使われている。Local Installation の章では /home/<ユーザー名>/nav2_ws/install/nav2_bringup だったが、ここでは container の中の場所になる。container の中では、プロンプトが root@… になる。この dev container の設定はユーザーを指定していないので、Dev Container の仕様の既定どおり、元の image の既定のユーザー（ここでは管理者の root）で動く。

ソースを直したら、直したパッケージだけをビルドし直す。workspace の直下（/opt/overlay_ws）で実行する。

# T2
colcon build --symlink-install --mixin $OVERLAY_MIXINS --packages-select <パッケージ名>
  • --mixin $OVERLAY_MIXINS: colcon の mixin（よく使うビルドの指定に名前を付けたもの）を使う。$OVERLAY_MIXINS は devcontainer.json で release ccache lld に決められていて、最適化したビルド（release）、コンパイルの結果を控えて再利用する道具（ccache。控えは /tmp/.ccache の volume に置かれる）、速いリンカ（lld）を使う指定になる。4 節の全体のビルドと同じ指定にそろえるために付ける。
  • --packages-select <パッケージ名>: 指定したパッケージだけをビルドする。

container の中は root なので、container の中で新しく作ったファイルは、WSL の側から見ると root の持ち物になる。ソースのフォルダは WSL と共有しているので、そこで新しいファイルを作ると、WSL の側で書き換えるときに sudo が要ることがある（想定。Docker の bind mount の一般の振る舞いから）。ビルドの結果は volume の /opt/overlay_ws に置かれるので、この問題は起きない。

VS Code の外の、WSL の普段のターミナルから container の中に入ることもできる。この dev container は、container に nav2 という名前を付ける設定になっている。

# T1
docker exec -it nav2 bash

docker exec は、動いている container の中で、コマンド（ここでは bash）を動かす。-it は、キーボードから打てるようにする指定である。公式の原稿は、この方法で開いた bash には、VS Code のターミナルと同じ環境の変数（VS Code と container をつなぐためのものなど）が設定されない、と注意している。ros2 のコマンドを使うだけなら、上と同じく source /opt/overlay_ws/install/setup.bash を実行すればよい（想定）。ただし、上のビルドで使った $OVERLAY_MIXINS と、ccache の控えの置き場所を決める変数は、devcontainer.json の remoteEnv で決められている。Dev Container の仕様では、remoteEnv は VS Code とそのターミナルにだけ渡り、container の全体には渡らない。そのため、ビルドは VS Code のターミナルで行う。VS Code を閉じると container が止まり、このコマンドは使えなくなる（想定。VS Code の既定の振る舞いから）。

6. 寿命と作り直し

公式の原稿は、container は使い捨てのもので、環境を作り直すたびに消して作り直される、と注意している。消えるもの・残るものは次のとおりである。

場所作り直すと例
container の中（下の 2 つ以外）消えるcontainer の中で apt install した道具、/root の設定
ソースのフォルダ（bind mount）残る（WSL のフォルダそのもの）/opt/overlay_ws/src/navigation2 の中の変更
volume残る/opt/overlay_ws のビルドの結果、/tmp/.ccache の控え

そのため、container の中で環境を変えたら、その変更を Dockerfile か devcontainer.json に書いておく。書いておけば、作り直しても同じ環境になり、チームのほかの人にも同じ変更が届く。volume は devcontainerId（その dev container に固有の、作り直しても変わらない名前）を付けた名前で作られるので、作り直しても同じ volume が使われ、ビルドをやり直さずに済む。

作り直すのは、主に次のときである。

  • Rebuild Container（コマンドパレットの Dev Containers: Rebuild Container）: Dockerfile や devcontainer.json を変えたとき、Nav2 の CI の image が新しくなったので取り込みたいとき。変わっていない部分は、前に作ったものを再利用する。
  • Rebuild Container Without Cache（Dev Containers: Rebuild Container Without Cache）: 前に作ったものを使わずに、最初から作る。設定は変えていないが、Dockerfile の中の apt upgrade などをやり直させたいとき。公式の原稿は、新しいパッケージが入ることがあるので、そのときは overlay の volume を消して、古いビルドの結果と混ざらないようにするとよい、と書いている。

手元の image・container・volume は、WSL のターミナルで次のように一覧できる。overlay- と ccache- で始まる 2 つの volume が、この dev container のものである。

# T1
docker image ls

docker ps -a

docker volume ls

期待する結果

DRIVER    VOLUME NAME
local     ccache-<英数字の並び>
local     overlay-<英数字の並び>

想定（Nav2 の devcontainer.json の volume の名前の付け方から）。docker volume ls の表示の例である。<英数字の並び> の部分が devcontainerId で、PC ごとに違う。VS Code の拡張機能が自分のために作る volume など、ほかの volume が並ぶこともある。docker image ls には、dev container 用に作った image（vsc-navigation2- で始まる名前と見込まれる）と hello-world などが、docker ps -a には nav2 という名前の container が並ぶ。

7. 画面と通信

このページでは、container の中から RViz2 や Gazebo の画面を出すことは扱わない。シミュレーションは、これまでどおり WSL で直接動かす。理由は次の 2 つである。

  • 既定の devcontainer.json では、container の外とつなぐ設定や、container の制限をゆるめる設定（下の表）が、どれもコメントにされて無効になっている。公式の原稿は、意図しない副作用や、container どうしの混線を避けるためと説明している。VS Code が手元の画面の仕組みを container に渡そうとすることはあるが、それで RViz2 や Gazebo が表示できるかは確かめていない。
  • Nav2 の Dockerfile には、画面をブラウザで見るための stage（visualizer）もあるが、古い Gazebo（Gazebo Classic）を前提にしている。このサイトでは新しい Gazebo（Harmonic）だけを扱う。

既定で無効になっている設定は、devcontainer.json の runArgs（container を起動するときに Docker に渡す指定）に、コメントとして並んでいる。公式の原稿の説明によると、それぞれ次のためのものである。

指定何をするか何のために
--network=hostcontainer が、WSL のネットワークをそのまま使うcontainer の外の ROS 2 の node と通信する（node どうしが互いを見つける仕組みが、container の外にも届くようにする）
--ipc=hostcontainer の外と、メモリを共有した通信をできるようにするcontainer の外の RViz2 などと、共有メモリで速く通信する
--pid=hostcontainer の外のプロセスが見えるようにする--network=host を使わずに、container の外の node を見つける
--privilegedcontainer に、PC の機器への広い権限を与えるUSB でつないだセンサーなどの機器を、container の中から使う
--cap-add=SYS_PTRACE・--security-opt=seccomp=unconfinedcontainer の安全のための制限をゆるめるgdb などでプログラムをデバッグする

どれも、container を PC から切り離す仕組みを弱める指定である。公式の原稿は、必要に応じて有効にし、範囲を広げたり絞ったりするよう勧めている。有効にするときは、何のためにどれを有効にしたかを、チームで分かる形で残す。

8. 安全のために

公式の原稿は、dev container を開く前に、開くフォルダとその作者を信頼できるかを確かめるよう注意している。dev container を開くと、Dockerfile と devcontainer.json に書かれたコマンドが自動で実行され、拡張機能が自動で入るからである。たとえば、他人の変更（pull request）を確かめるために開くときは、その変更に悪意のあるコードが含まれていないかを先に見る。VS Code がフォルダを信頼するかを尋ねるのは、このためである。

Nav2 の jazzy ブランチの設定では、開く前に、とくに次の 2 つを確かめておく（4 節の「開く前に確かめる」の詳しい説明）。どちらも、製品を開発する会社では、会社の決まりに照らして判断が要りうるものである。

  • 自動で入る拡張機能: devcontainer.json の extensions に、ROS・CMake・Git の補助の拡張機能と並んで、AI がコードを補う GitHub Copilot（GitHub.copilot）がある。使うと、編集中のコードが外部のサービスに送られうる。入れたくなければ、開く前に extensions の一覧から外す（Nav2 のソースのファイルを変えることになるので、git diff に出る）。
  • 自動で同意するライセンス: Dockerfile は、ROS 2 の通信の実装の 1 つである RTI Connext DDS を含むパッケージ（ros-jazzy-rmw-connextdds）を入れる。その前に、RTI_NC_LICENSE_ACCEPTED=yes という、名前からしてライセンスへの同意を自動で済ませる設定を置いている。ROS 2 の公式の文書によると、RTI Connext DDS が無償なのは、試作・研究・非商用・学術の用途である。製品に使うなら、ライセンスを別に確かめる。

このほかにも、container を作るときに自動で起きることがある。devcontainer.json の features（image に足す部品の指定）で、GitHub をコマンドで操作する道具（GitHub CLI）が入る。また、onCreateCommand のスクリプトは、container の中の git に、どのフォルダのリポジトリも持ち主を問わず信頼する設定（safe.directory "*"）を入れる。どちらも container の中だけの設定である。

9. 製品に組み込むなら

  • 開発の環境をそろえる。自分たちの製品のリポジトリにも .devcontainer を置けば、チームの全員と CI が同じ環境でビルドできる。Nav2 の設定のように、CI と同じ Dockerfile を使い、CI が作った image を控えに使うと、「手元では通るのに CI では通らない」が減る。
  • 配る形にも Docker を使える。公式の Build and Install の Docker Installation は、Nav2 のリポジトリの Dockerfile から docker build で image を作る方法と、Nav2 の版ごとに作られた image（nav2_docker）を使う方法を挙げている。ロボットに載せる PC へ、決まった版の Nav2 を image ごと届ける形も考えられる。どの image のどの版を使ったかは、Local Installation の章の 6 節のコミットと同じく記録する。
  • ライセンスと利用の条件を確かめる。image に入るもの（8 節の RTI Connext DDS など）と、使う道具（Docker Desktop を選ぶ場合はその利用の条件）を、製品に使ってよいかの観点で確かめる。
  • container の権限を絞る。7 節の指定は、開発には便利だが、PC から切り離す仕組みを弱める。ロボットで container を動かすときは、要るものだけを有効にする。
