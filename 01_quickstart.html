Quickstart：シミュレーションのロボットを Nav2 で動かす

ロボットと、与える初期位置（4 節）与える目標と、Nav2 が引く経路（5 節）

Nav2 を自分たちの製品に組み込もうと考えたとき、最初に知りたいのは「Nav2 を入れると、何が、どう動くのか」だろう。仕組みの説明を読む前に、まず動くものを見ておくと、後の章の話がどこにつながるのかが分かりやすくなる。

このページでは、シミュレーターの中の小さなロボット（TurtleBot 3）を、Nav2 で目的地まで走らせる。コマンドを 1 つ打つと、シミュレーター・Nav2・地図を見る画面がまとめて立ち上がる。あとは画面の上で「ロボットは今ここにいる」「ここへ行ってほしい」と 2 回指示するだけで、ロボットは自分で経路を考え、壁を避けて進んでいく。

このページについて

  • Nav2 の公式の文書の Quickstart（jazzy 版の原稿、コミット b22554c）を基に、日本語で説明し直したもの。逐語の翻訳ではない。出典とライセンスはページの末尾にある。
  • ROS 2 Jazzy と Ubuntu 24.04（Windows の WSL2 を含む）を前提にする。ROS 2 の導入は、環境構築の章で済ませておく。
  • 期待する結果の出どころ: ターミナルに出る表示（2 節〜7 節のコードの箱）は、作成時の環境（navigation2 1.3.14、nav2_minimal_turtlebot_simulation 1.0.1）で実際に確かめたもの。ただし 3 節〜7 節は、Gazebo と RViz の画面を出さずに起動し、RViz での初期位置と目標の指定は、同じ内容をコマンドで送って確かめた。Gazebo と RViz の画面の見え方と、RViz の操作（3 節〜5 節と 7 節の画面の説明）は、ソースと公式の説明から想定したもので、まだ実際の画面と照らし合わせていない。
  • ログの角括弧の中の長い数字は時刻（UNIX 時刻）で、実行するたびに変わる。-6 のような番号、pid（プロセスの番号）、名前の後ろに付く数字・英数字も、実行するたびに変わることがある。

0. 学習目標と完了条件

このページを終えると、次のことができる。

  1. Nav2 と、シミュレーションの TurtleBot 3 のパッケージを入れられる。
  2. 1 つのコマンドで、シミュレーター・Nav2・RViz（地図を見て指示を出す画面）をまとめて起動できる。
  3. RViz で初期位置と目標を与え、ロボットを目標まで動かせる。
  4. 起動した node と topic を、ros2 コマンドで確かめられる。

完了条件は、RViz で指定した目標まで、ロボットが自分で走って止まること。

1. 全体像

このページで起動するものは、大きく 4 つの役に分かれる。ROS 2 では、1 つの役目を持つプログラムの単位を node と呼び、node どうしは、決まった型のデータを流す名前つきの通り道である topic でつながる。下の図で、横の矢印に付けた英語の名前（scan など）が、topic の名前である。縦の矢印の言葉は運ぶものの説明で、topic の名前ではない（目標は、5 節で見る action という別の仕組みで送られる）。

  • Gazebo: ロボットと、ロボットが走る世界（壁や柱）を計算で再現するシミュレーター。レーザーの距離センサーの値や、車輪の回転から求めた移動量を作り出し、速度の指令を受けると車輪を回す。
  • ros_gz_bridge: Gazebo と ROS 2 は別の仕組みで通信しているので、その間でデータを受け渡す node。Gazebo の値を ROS 2 の topic として出し、ROS 2 の速度の指令を Gazebo に渡す。
  • Nav2: ロボットの位置を推定し、目標までの経路を考え、その経路に沿って走るための速度の指令を出す。実体は、主なものだけで 14 個の node の集まりである（6 節で確かめる）。
  • RViz: ROS 2 のデータを画面に描く道具。地図・ロボットの位置・経路を表示し、このページでは初期位置と目標を Nav2 に伝える入り口にもなる。

矢印の topic は、それぞれ次のデータを運ぶ。scan はレーザーで測った周囲の距離（型は sensor_msgs/msg/LaserScan）、odom は車輪の回転から求めた移動量（odometry。型は nav_msgs/msg/Odometry）、tf は座標系どうしの位置関係（型は tf2_msgs/msg/TFMessage）、cmd_vel は Nav2 がロボットに出す速度の指令（型は geometry_msgs/msg/Twist）。図では省いたが、シミュレーターの時計を配る /clock（型は rosgraph_msgs/msg/Clock）も Gazebo から流れている。ロボットの各部品の位置関係を tf として配る robot_state_publisher という node も、一緒に起動する。

2. Nav2 を入れる

Nav2 本体（ros-jazzy-navigation2）、起動のための設定と launch file（どの node を、どの設定で起動するかを書いたファイル。3 節で使う）をまとめたパッケージ（ros-jazzy-nav2-bringup）、シミュレーションの TurtleBot 3（ros-jazzy-nav2-minimal-tb3-sim など）を、apt で入れる。

入れる前に sudo apt upgrade で、すでに入っている ROS 2 のパッケージを新しい版にそろえておく。Nav2 の一部を前に入れたまま更新せずに残りを足すと、新しい版の起動の設定を古い版の本体で読むことになり、食い違いで起動に失敗することがある。

sudo apt update

sudo apt upgrade

sudo apt install ros-jazzy-navigation2 ros-jazzy-nav2-bringup 'ros-jazzy-nav2-minimal-tb*'

最後の行の 'ros-jazzy-nav2-minimal-tb*' は、名前が ros-jazzy-nav2-minimal-tb で始まるパッケージをまとめて指定する書き方で、TurtleBot 3 と TurtleBot 4 のシミュレーションの部品が入る。引用符で囲むのは、* を bash に解釈させず、そのまま apt に渡すため。地図を作る slam_toolbox も、依存するパッケージとして一緒に入る。

入ったら、Nav2 のパッケージの版がそろっているかを確かめる。

dpkg-query -W -f='${Version}\n' 'ros-jazzy-nav2-*' ros-jazzy-navigation2 | cut -d- -f1 | sort | uniq -c

期待する結果

      3 1.0.1
     32 1.3.14

左の数が、その版のパッケージの数である。1.0.1 の 3 個はシミュレーションのロボットの部品で、Nav2 本体とは別に版を数えているので、これで正しい。それ以外の Nav2 のパッケージが 1 つの版（ここでは 1.3.14）にそろっていればよい。版の番号そのものは、更新されると変わる。1.0.1 の行を除いて 2 つ以上の版が並んだら、sudo apt upgrade をやり直す。

3. 起動する

起動したら、すぐに 4 節の操作（RViz で初期位置を与える）をする。初期位置を与えないまま時間がたつと、Nav2 の移動を受け持つ側が起動をあきらめてしまう（作成時の環境では約 85 秒。この節の最後で説明する）。先に 4 節まで読んでから起動するとよい。

ターミナルを開き、次の 2 行を実行する。コマンドの箱の 1 行めの # T1 は、「1 つめのターミナルで実行する」という印である（# から後はコメントなので、打たなくてよい）。6 節では、2 つめのターミナルを # T2 で表す。

# T1
source /opt/ros/jazzy/setup.bash

ros2 launch nav2_bringup tb3_simulation_launch.py headless:=False

1 行めの source は、ROS 2 のコマンドとパッケージの場所を、今のターミナルに教える。ターミナルを新しく開くたびに必要になる。

2 行めの ros2 launch は、launch file に書かれた複数の node を、設定と一緒にまとめて起動するコマンドである。ここでは nav2_bringup パッケージの tb3_simulation_launch.py を使う。この launch file は Python で書かれている（launch file は XML や YAML でも書ける）。

最後の headless:=False は、launch file に渡す引数である。headless は「Gazebo の画面を出さずに動かすか」を表し、既定では True（画面を出さない）になっている。ロボットの動きを目で見るために、False にしている。

この launch file は、図 1 の 4 つに加えて、Gazebo の中にロボットを置く処理と robot_state_publisher を起動する。地図には nav2_bringup に入っている tb3_sandbox、ロボットには TurtleBot 3 の waffle という型が使われる。Windows の WSL2 でも、Windows 11 なら Linux の画面のアプリがそのまま Windows のウィンドウとして開く。

期待する結果

T1 には大量のログが流れる。数秒〜十数秒で、次の行が出る（作成時は起動から約 7 秒）。

[component_container_isolated-6] [INFO] [1795242858.189862897] [lifecycle_manager_localization]: Managed nodes are active

Nav2 の node は、lifecycle_manager_ で始まる 2 つの係が、決まった順番で動かし始める（この launch file では、それを自動で始める設定 autostart が既定で true になっている）。上の行は、位置の推定を受け持つ側（lifecycle_manager_localization）が、受け持つ node をすべて動かし終えたという知らせである。

一方、移動を受け持つ側（lifecycle_manager_navigation）は、この時点ではまだ動き終えない。経路を考える部品が「地図の上のどこにロボットがいるか」を必要としているのに、それがまだ分からないからである。代わりに、次の警告が繰り返し出る（次の行は、上の行とは別の回に起動したときの表示なので、時刻が前後している）。

[component_container_isolated-6] [WARN] [1795242413.769624260] [amcl]: AMCL cannot publish a pose or update the transform. Please set the initial pose...

AMCL（レーザーで測った周囲の距離と地図を照らし合わせて、ロボットの位置を推定する node。4 節で詳しく見る）が「初期位置を与えてほしい」と言っている。4 節で初期位置を与えると止まる。

画面では、ウィンドウが 2 つ開く。

  • Gazebo: 壁と柱のある世界の中に、TurtleBot 3 が置かれている。
  • RViz: 白と黒の地図が表示されている。この時点では、まだロボットの位置は定まっていない。

初期位置を与えずに待ちすぎたとき

移動を受け持つ側は、ロボットの位置が分かるのを、決まった時間だけ待つ。その間に 4 節の初期位置を与えないと、起動をあきらめてしまう。作成時の環境では、起動から約 85 秒後に、次のエラーが出た。

[component_container_isolated-6] [ERROR] [1795242475.734356106] [global_costmap.global_costmap]: Failed to activate global_costmap because transform from base_link to map did not become available before timeout
[component_container_isolated-6] [ERROR] [1795242475.735565668] [lifecycle_manager_navigation]: Failed to change state for node: planner_server
[component_container_isolated-6] [ERROR] [1795242475.735696263] [lifecycle_manager_navigation]: Failed to bring up all requested nodes. Aborting bringup.

1 行めは、経路を考えるための costmap（ロボットがぶつかる危険の大きさを地図のマスごとに表したもの。4 節で画面に現れる）が、地図（map）とロボットの体（base_link）の位置関係を時間内に得られなかった、という意味である。続く 2 行で、移動を受け持つ側が起動を打ち切ったことが分かる。この状態では、目標を与えてもロボットは動かない。7 節の方法（T1 で Ctrl+C）でいったん止め、もう一度起動して、今度は早めに 4 節の初期位置を与える。

4. 初期位置を与える

起動した直後の Nav2 は、ロボットが地図のどこにいるかを知らない。位置を推定するのは、3 節の警告に出てきた AMCL という node で、レーザーで測った周囲の距離と地図を照らし合わせ、「地図のこのあたりにいるはずだ」と推定し続ける。ただし、照らし合わせを始めるには、だいたいの出発点が要る。それを人が与えるのが、この節の操作である。

この launch file は、ロボットを地図の (x, y) = (-2.0, -0.5) 付近に、地図の x の正の向きを向けて置く。Gazebo の画面でロボットがいる場所を見て、RViz の地図の同じ場所を探す。見つけたら、次のように操作する。

  1. RViz の上の端にある道具の並び（ツールバー）で、「2D Pose Estimate」を押す。
  2. 地図の上で、ロボットがいる点を押し、押したまま、ロボットの正面の向きへドラッグして離す。押した点が位置に、ドラッグした向きがロボットの向きになる。

期待する結果

ロボットの周りに、小さな矢印の群れ（particle cloud）が現れる。これは AMCL が考えている「ロボットがいるかもしれない位置」の候補の集まりで、ロボットが動くにつれて 1 か所に集まっていく。地図の上には、壁の周りに色の付いた帯（costmap）も現れる。costmap は、ロボットがぶつかる危険の大きさを地図のマスごとに表したもので、Nav2 はこれを見て経路を考える。

位置が多少ずれていてもかまわない。走り出すと、AMCL が少しずつ正しい位置に寄せていく。大きくずれたときは、もう一度「2D Pose Estimate」で与え直せばよい。

T1 のログには、AMCL が初期位置を受け取ったことと、移動を受け持つ側が動き終えたことが出る（作成時は、初期位置を与えてから約 3.5 秒後）。

[component_container_isolated-6] [INFO] [1795242860.608735354] [amcl]: Setting pose (2.613000): -2.000 -0.500 0.000
[component_container_isolated-6] [INFO] [1795242864.088389389] [lifecycle_manager_navigation]: Managed nodes are active

1 行めの -2.000 -0.500 0.000 は、与えた初期位置（地図の上の x と y〈メートル〉、向き〈ラジアン〉）である。その前の括弧の中の数字は、シミュレーターの時計での時刻（秒）で、実行するたびに変わる。作成時は x が -2.0、y が -0.5、向きが 0（地図の x の正の向き）の位置を与えた。これは、この launch file がロボットを置く位置と同じである。2 行めが出れば、Nav2 全体が動ける状態になっている。

5. 目標を与えて動かす

  1. RViz のツールバーで「Nav2 Goal」を押す。
  2. 地図の上で行き先の点を押し、着いたときに向いていてほしい方へドラッグして離す（図 2 と同じ操作）。

RViz は、この目標を Nav2 の bt_navigator という node に送る。送る仕組みは action と呼ばれ、「目標まで行く」のように時間のかかる依頼を送り、途中の経過と最後の結果を受け取れる。bt_navigator は依頼を受けると、経路を考える planner_server と、経路に沿って走らせる controller_server に順に仕事を割り振る。

期待する結果

RViz の地図に、ロボットから目標までの経路の線が引かれ、ロボットがその線に沿って走り出す。Gazebo の画面でも、同じようにロボットが動く。目標に着くと、指定した向きに向き直って止まる。ページの冒頭の図が、この流れを表している。

途中で止めたいときは、RViz の左下の Nav2 の欄にある取り消しのボタンを押す。

T1 のログには、走り始めと到着が出る。作成時は、スタートから x の正の向きへ約 1 m 先（x が -1.0、y が -0.5）を目標にした。

[component_container_isolated-6] [INFO] [1795242870.777356354] [bt_navigator]: Begin navigating from current location (-1.96, -0.52) to (-1.00, -0.50)
[component_container_isolated-6] [INFO] [1795242873.249784538] [controller_server]: Reached the goal!
[component_container_isolated-6] [INFO] [1795242873.278012470] [bt_navigator]: Goal succeeded

1 行めの「current location」は、AMCL が推定した今の位置で、与えた初期位置（-2.0, -0.5）から少しずれている。走り出す前でも、AMCL がレーザーの測定と地図を照らし合わせて、推定を寄せ直しているためと考えられる。Goal succeeded が出れば、目標に着いている。

6. 何が動いていたか

起動したままの状態で、もう 1 つターミナルを開き、どんな node と topic が動いているかを確かめる。新しいターミナルでは、最初に source が要る。

source /opt/ros/jazzy/setup.bash

ros2 node list

ros2 topic list

Nav2 の主な node は 14 個ある。位置の推定を受け持つのが map_server（地図を配る）・amcl・lifecycle_manager_localization の 3 個、移動を受け持つのが bt_navigator・planner_server・controller_server・smoother_server・route_server・behavior_server・velocity_smoother・collision_monitor・waypoint_follower・docking_server・lifecycle_manager_navigation の 11 個である。lifecycle_manager_ で始まる 2 つは、ほかの node を決まった順番で動かし始め、止める係である。global_costmap・local_costmap は、planner_server と controller_server がそれぞれ中に持つ costmap、bt_navigator_ で始まる 2 つは bt_navigator が中で使う node である。/launch_ros_ と /transform_listener_impl_ の後ろの数字・英数字は、実行するたびに変わる。

これだけの数の node があるが、この launch file の既定では、Nav2 の node は nav2_container という 1 つのプロセスの中にまとめて入れられている（use_composition が既定で True）。

ros2 topic list には、topic の名前が並ぶ。ただし作成時の環境（ほかの PC の ROS 2 と混ざらないよう、node を探す範囲をその PC の中だけに限る設定 ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST にしていた）では、次の 11 個しか表示されなかった。/map など、nav2_container の中の node の topic が抜けている。

ros2 topic list --no-daemon --spin-time 10

最後に、ロボットが走っている間に Nav2 が出す速度の指令を、1 つだけ読んでみる。この時点のロボットは 5 節の目標に着いて止まっているので、先に T2 で次のコマンドを実行してから、RViz の「Nav2 Goal」で別の目標を与える。コマンドは、指令が 1 つ流れてくるまで待ち、受け取ると表示して終わる。待ち続けて止めたいときは、Ctrl+C を押す。

# T2
ros2 topic echo /cmd_vel --once

期待する結果

linear:
  x: 0.1441907286643982
  y: 0.0
  z: 0.0
angular:
  x: 0.0
  y: 0.0
  z: 0.0
---

型は geometry_msgs/msg/Twist（1 節）で、linear.x が前に進む速さ（メートル毎秒）、angular.z がその場で向きを変える速さ（ラジアン毎秒）である。上の値は、作成時に 5 節の目標（正面の約 1 m 先）へ向かう途中で読んだもので、前向きに約 0.14 m/s、向きを変える速さは 0 だった。別の目標を与えて読むと、向かう方向によっては angular.z も 0 でない値になる。値は、読んだ瞬間によって変わる。

topic の一覧にあった /cmd_vel_nav と /cmd_vel_smoothed は、この指令ができるまでの途中の段である。controller_server が出した指令（/cmd_vel_nav）を、velocity_smoother が急な変化をならし（/cmd_vel_smoothed）、collision_monitor がぶつかりそうなら止めたうえで、/cmd_vel としてロボットに渡している。

7. 止め方

T1（ros2 launch を実行したターミナル）で Ctrl+C を押す。launch file で起動した node がまとめて止まり、Gazebo と RViz のウィンドウも閉じる。

期待する結果

node が止まっていくログが流れ、数秒〜十数秒でコマンドの入力に戻る。作成時は 2 回とも、終わり際に次のようなエラーが出た。

[component_container_isolated-6] Magick: abort due to signal 11 (SIGSEGV) "Segmentation Fault"...
[ERROR] [component_container_isolated-6]: process[component_container_isolated-6] failed to terminate '5' seconds after receiving 'SIGINT', escalating to 'SIGTERM'
[INFO] [component_container_isolated-6]: sending signal 'SIGTERM' to process[component_container_isolated-6]
[ERROR] [component_container_isolated-6]: process has died [pid 20842, exit code -6, cmd '/opt/ros/jazzy/lib/rclcpp_components/component_container_isolated --ros-args ...

Nav2 の node を入れた container（6 節の nav2_container）のプロセスが、止まる途中で異常な終わり方をした、という表示である。Ctrl+C の合図（SIGINT）で 5 秒以内に止まらなかったので、より強い合図（SIGTERM）が送られている。見た目は物々しいが、作成時はどちらの回も、関連するプロセスはすべて止まっていた。気になるときは、次のコマンドで、この launch file が起動した主なプロセスが残っていないことを確かめられる。

pgrep -af 'gz sim|component_container|parameter_bridge|robot_state_publisher|rviz2'

期待する結果

何も表示されなければ、残っているプロセスは無い。6 節の ros2 node list などが裏で起動した daemon（_ros2_daemon）は、次に ros2 コマンドを速く動かすために、わざと残る作りになっている。止めたいときは ros2 daemon stop で止められる。

8. 製品に組み込むなら

このページでは、ロボットの体も、地図も、指示を出す人も、すべてシミュレーションと手の操作で代わりに用意した。製品では、それぞれを本物に置き換えることになる。

このページで代わりに担っていたもの製品では
Gazebo と ros_gz_bridge が出す scan・odom・tf、受け取る cmd_vel実機のセンサーと車輪のドライバが、同じ名前と型の topic を出し、受け取る。同じ topic をそろえることが、Nav2 につなぐための出発点になる。ロボットの大きさや速度の上限などの設定は、自分のロボットに合わせて変える。
robot_state_publisher が配る、TurtleBot 3 の形（ロボットの形を記述するファイル URDF）と座標系の名前（base_link など）自分のロボットの形を URDF で書き、座標系の名前を Nav2 の設定とそろえる。
/clock が配るシミュレーターの時計（use_sim_time〈node がシミュレーターの時計を使うかどうかの設定〉が true）実機では、コンピューターの時計を使う（use_sim_time を false にする）。Nav2 は時刻のずれに敏感なので、どの時計を使うかをそろえることが大切になる。
あらかじめ用意された地図 tb3_sandboxロボットを走らせる場所の地図を、自分で作る。
RViz で手で与えた初期位置と目標製品のアプリケーションから、プログラムで与える。

地図の作り方、プログラムからの指示の出し方、自分のロボットに合わせた設定は、この教材の後の章で扱う。
