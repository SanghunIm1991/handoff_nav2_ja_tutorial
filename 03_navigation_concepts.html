Navigation Concepts：Nav2 を形作る考え方

Quickstart の章では、RViz で目標を与えると、ロボットが自分で経路を考えて走った。そのとき Nav2 の中では、10 を超える node が、決まった仕組みで仕事を分け合っていた。このページでは、その仕組みを順に見ていく。

扱うのは、Nav2 の公式の文書が「Nav2 を理解して使うために要る考え方」としてまとめているものである。ROS 2 の 2 つの仕組み（action と lifecycle）、仕事の流れを決める behavior tree、実際の計算をする各サーバー、ロボットの位置の推定、周りの環境の表し方。各節では、Quickstart と同じシミュレーションを動かしたまま、その考え方が実際にどう現れているかを、読み取りだけのコマンドで確かめる。

このページについて

  • Nav2 の公式の文書の Navigation Concepts とその下の 5 つのページ（jazzy 版の原稿、コミット b22554c）を基に、日本語で説明し直して 1 つのページにまとめたもの。逐語の翻訳ではない。公式の原稿には実習が無く、各節のコマンドはこのページで足したものである。出典とライセンスはページの末尾にある。
  • ROS 2 Jazzy と Ubuntu 24.04（Windows の WSL2 を含む）を前提にする。Quickstart の章を終えていることを前提にする。
  • 期待する結果の出どころ: 2 節〜7 節の表示は、作成時の環境（navigation2 1.3.14 を apt で入れた環境）で、Gazebo と RViz の画面を出さずにシミュレーションを起動し、初期位置をコマンドで与えてから取ったもの。画面を出した形では確かめていない。
  • ログの角括弧の中の長い数字は時刻（UNIX 時刻）で、実行するたびに変わる。At time の後の数字は、シミュレーターの時計の秒数である。

0. 学習目標と完了条件

このページを終えると、次のことができる。

  1. Nav2 が action と lifecycle node をどう使っているかを説明できる。
  2. behavior tree と各サーバー（planner・controller・smoother・behavior・route）の役目と、その間のつながりを説明できる。
  3. map → odom → base_link の座標系と、それぞれを誰が配るかを説明できる。
  4. costmap とその層が何をしているかを説明できる。

完了条件は、2 節〜7 節のコマンドを動いている Nav2 に対して実行し、表示を本文の説明と結び付けて読めること。

1. 全体像と準備

Nav2 の中心には、bt_navigator という node がいる。目標を受け取ると、behavior tree（4 節）に書かれた手順に沿って、実際の計算をするサーバー（図 1 の 5 つ）に仕事を頼む。頼むときに使うのが、ROS 2 の action（2 節）である。

これらは、Quickstart の章の 6 節で ros2 node list に出てきた node である。このページのコマンドを試すには、Quickstart と同じシミュレーションを動かしておく。T1 で起動し、すぐに RViz で初期位置を与える（Quickstart の章の 3 節・4 節。遅れると移動の側の起動が打ち切られる）。# T1 は「1 つめのターミナルで実行する」という印で、# から後はコメントなので打たなくてよい（このページのほかのコマンドの箱でも同じ）。

# T1
source /opt/ros/jazzy/setup.bash

ros2 launch nav2_bringup tb3_simulation_launch.py headless:=False

このページの 2 節〜7 節のコマンドは、どれも 2 つめのターミナル（T2）で実行する。T2 を開いたら、2 節の最初の箱のとおり、最初に 1 回だけ source /opt/ros/jazzy/setup.bash を実行しておく。このページの表示は、apt で入れた Nav2 で取ったものである。Local Installation の章でビルドした Nav2 で起動した場合は、作成時は確かめていない（作成時に一度、ビルドした Nav2 を読み込んだ環境で試したときは、2 節と 3 節のコマンドの表示が空だった。原因は確かめていない）。

2. ROS 2 の仕組み（1）: action

action は、時間のかかる仕事を別の node に頼む ROS 2 の仕組みである。頼む側を action client、受ける側を action server と呼ぶ。頼む内容（要求）を送ると、仕事の途中で経過（feedback）が届き、終わると結果（result）が返る。公式の文書の例では、ブルドーザーのショベルを持ち上げる仕事なら、要求は角度、途中経過は残りの角度、結果は成功か失敗と最後の角度になる。ナビゲーションなら、要求は目標の位置、途中経過は走った時間と目標までの距離、結果は成功したかどうかである。要求・途中経過・結果の型は、.action のファイルで決める。

Nav2 は、ROS 1 の頃のナビゲーションより action を多く使い、仕事によっては手軽に頼める topic の口が無いものもある。そのため、Nav2 を使う開発者にとって、action は特に大事な仕組みである。

プログラムから頼むときは、頼んだ結果を「後で受け取る約束」（future）として受け取る。C++ の std::future と同じ考え方で、結果が出るまで待ってもよいし、待たずにほかの処理を進め、ときどき終わったかを確かめてもよい。途中経過と結果は、関数を登録しておいて呼んでもらう（コールバック）こともできる。どちらの受け取り方でも、頼む側の node を動かし続けて（spin して）、届いたものを処理させる必要がある。action を頼むプログラムの書き方は、後の章（Python から Nav2 に指示を出す章。準備中）で扱う。

Nav2 では、いちばん上の入り口が NavigateToPose という action で、bt_navigator が受ける。bt_navigator は、さらに各サーバーの小さな action を呼んで、経路の計算・経路の追従・困ったときの動きを頼む。それぞれの .action の型は、nav2_msgs というパッケージにある。

3. ROS 2 の仕組み（2）: lifecycle node と bond

lifecycle node（managed node とも呼ぶ）は、起動と終了の手順を、決まった状態の移り変わりとして持つ ROS 2 の node である。起動や終了の順番が毎回同じになるので、動きを予測しやすく、製品として使うときや不具合を調べるときにも、プログラムを整理しやすい。詳しくは ROS 2 の 設計の文書にある。

  • unconfigured: 起動した直後。コンストラクタだけが動いた状態である。コンストラクタには、通信の準備や parameter の読み込みを書かない決まりになっている。
  • inactive: 設定の段階（on_configure()）を経た状態。parameter・通信の口を準備し、安全が大事なシステムでは、使うメモリもここで確保しておく。
  • active: 動き出す段階（on_activate()）を経た状態。通信の口が働き、処理を始める。
  • finalized: 終わるときは、止める・片づける・終える段階を順に経て、ここに至る。

Nav2 のサーバーは、どれも lifecycle node である。状態を順に進める役は、lifecycle manager が受け持つ。Quickstart で見た lifecycle_manager_localization と lifecycle_manager_navigation がそれで、すべてを active にし終えると Managed nodes are active を出す。

Nav2 は、ROS 2 の lifecycle node を包んだ nav2_util の LifecycleNode を使う。これには、lifecycle manager との間の bond（つながりを見張る仕組み）が入っている。active になったサーバーが落ちると、bond を通じて lifecycle manager が気づき、システム全体を止めて、大きな故障を防ぐ。

amcl が active の状態にある。角括弧の数は状態の番号で、lifecycle_msgs/msg/State で unconfigured が 1、inactive が 2、active が 3、finalized が 4 と決まっている。Quickstart の章の 3 節で、初期位置を待ちすぎると起動が打ち切られたのは、planner_server が中の global_costmap を active にできず（座標系のつながりがそろわないため。6 節）、移動の側の lifecycle manager が planner_server を active に進められずに、起動を打ち切ったからである。

4. behavior tree

behavior tree（BT）は、やるべき仕事を木の形に並べて、複雑な手順を組み立てる方法である。よく比べられるのが有限状態機械（FSM）で、状態と遷移で手順を書く。公式の文書は、サッカーをするロボットの例を挙げている。FSM では、状態が数十、遷移が数百にもなりうる。サッカーの判断を FSM に埋め込むのは難しく、誤りやすい。「左・右・真ん中のどこからシュートするか」のような選択も書きにくい。BT なら、「蹴る」「歩く」「ボールへ行く」といった基本の動きを部品として作り、いろいろな振る舞いで使い回せる。BT の考え方は、公式の文書が勧める本の 1〜3 章（30 分ほどで読める）にまとまっている。

Nav2 は、BT のライブラリとして BehaviorTree.CPP の V4 を使う。木の 1 つ 1 つの節（BT の node）は plugin（実行時に読み込む部品のライブラリ。5 節で詳しく見る）として作られ、bt_navigator の中で組み合わされる。木の形は XML のファイルに書き、読み込むときに、XML の中の名前と登録された plugin が結び付けられる。あとは木を順にたどれば、ナビゲーションが進む。

このライブラリを使う理由の 1 つは、木を別の木の一部（subtree）として読み込めることである。たとえば、サッカーの大きな木の中の「ボールへ行く」の節に、Nav2 の木をそのまま使える。また、手順を BT に集め、各サーバーは BT を通じてデータをやり取りするだけにしておくと、手順が正しいかを道具で検証しやすくなる。

# T2
ros2 param get /bt_navigator default_nav_to_pose_bt_xml

期待する結果

String value is: /opt/ros/jazzy/share/nav2_bt_navigator/behavior_trees/navigate_to_pose_w_replanning_and_recovery.xml

navigate_to_pose の目標を受けたときに使う木の XML の場所である。名前のとおり、経路を計算し直しながら進み（replanning）、困ったら回復の動き（recovery）を試す木になっている。less などでこのファイルを開くと、木の形が XML で書かれているのが見える。Local Installation の章でビルドした Nav2 で起動した場合は、~/nav2_ws/install の下の同じ名前のファイルが表示される。

5. 各サーバー

図 1 の 5 つのサーバー（planner・controller・smoother・behavior・route）は、どれも action server で、実際の計算は中に読み込んだ plugin（実行時に読み込む部品のライブラリ。ROS 2 の pluginlib の仕組み）が行う（route_server だけは少し違う。下の route の項）。

planner・controller・smoother のサーバーは、起動するときに、使うアルゴリズムの「名前」と「種類」の組を設定で受け取る。種類は pluginlib に登録された plugin の名前で、名前はその仕事に付ける呼び名である。たとえば、経路に沿って走る controller に FollowPath という名前を付けると、そのアルゴリズムの parameter は FollowPath.<parameter の名前> の形で置く。behavior tree の節がサーバーを呼ぶと、サーバーは名前でアルゴリズムを選んで実行する。こうしておくと、BT の側は「経路に沿って走る」という仕事の種類だけを書けばよく、どのアルゴリズムを使うかは設定で変えられる。1 つのサーバーに複数の plugin を置いて、経路の追従・充電台へのドッキング・道具の操作などを使い分けることもできる。そのとき、二重に持つと計算の費用がかさむ環境の表し方（7 節の costmap）を、1 つのサーバーの中で共有できる。

# T2
ros2 param get /controller_server FollowPath.plugin

ros2 param get /planner_server GridBased.plugin

ros2 param get /behavior_server behavior_plugins

期待する結果

String value is: nav2_mppi_controller::MPPIController
String value is: nav2_navfn_planner::NavfnPlanner
String values are: ['spin', 'backup', 'drive_on_heading', 'assisted_teleop', 'wait']

Quickstart の既定の設定では、FollowPath という名前に MPPI という controller が、GridBased という名前に NavFn という planner が当てられている。behavior_server には、5 つの動き（その場で回る・下がる・決まった向きに進む・人の操作を補助する・待つ）が読み込まれている。設定のファイルでこの種類を書き換えれば、BT を変えずにアルゴリズムを替えられる。

  • planner: 目標までの経路を計算する。代表的なのは、今の位置から目標までの経路と、空いている場所をくまなく回る経路（カバレッジ）である。全体の地図を表す global costmap と、そこに取り込んだセンサーの値を使う。
  • controller: planner が計算した経路に沿って走るための速度の指令を、周期ごとに計算する（ROS 1 では local planner と呼ばれていた）。ロボットの周りを表す local costmap を使い、ロボットを少し先まで動かしたと仮定して、実際に走れる動きを選ぶものが多い。経路の追従のほか、充電台へのドッキング、エレベーターへの乗り込みなどの plugin も作れる。
  • smoother: planner の経路を受け取り、ぎざぎざや急な向きの変化をならしたり、障害物から離したりして、よくした経路を返す。planner と別にしておくと、planner と smoother の組み合わせを変えたり、経路の一部だけをならしたりできる。
  • behavior: 主な用途は、困った状況から抜け出すための動き（recovery）。センサーの誤りで costmap が偽の障害物だらけになったら costmap を消す、動く障害物や下手な制御で動けなくなったら下がる・その場で回る、どうにもならなければ人に助けを求める、などである。behavior_server は、動きごとに別の action を出す（動きによって頼む内容が違うため）。また、controller_server の local costmap を受け取って使い、costmap を二重に持たないようにしている。recovery に限らず、costmap や tf のような重い資源を共有したい動きなら、何でも behavior_server に置ける。
  • route: 空いている場所を自由に探すのではなく、あらかじめ用意した道のグラフ（点とその間の向きのある辺）の上で、最もよい道順を計算する。車線、走ってよい場所、教えた道を繰り返す経路、街の道路などを表せる。route_server はほかのサーバーと違い、道順の計算は自分で行い、plugin は辺の採点やグラフのファイルの読み込みなどを受け持つ。

新しいアルゴリズムが要るときは、まず plugin として足すことを考える。今のサーバーの口で足りなければ、新しいサーバーとそれを呼ぶ BT の node を作ってもよく、どちらの場合も Nav2 のリポジトリそのものを書き換える必要は無い。

ロボットの外形（footprint）

costmap は、ロボットの外形（footprint）を、半径 robot_radius の円か、点の並び footprint で表す多角形として持つ。円でないロボットは多角形にする。外形は ~/footprint の topic で途中から変えることもでき、腕を伸ばした・荷物を載せたなど、形が変わったときに planner と controller が新しい形を使う。

6. 位置の推定

Nav2 が求めるのは、座標系（frame）の間の 2 つのつながりである。ROS の決まり REP 105 は、少なくとも map → odom → base_link → センサーの座標系、とつながった木を作ることを求めている。座標系どうしの時刻つきの位置関係は、ROS 2 の tf2 というライブラリで扱う（Quickstart の章の tf の topic）。

  • map → odom: 地図の上のどこにいるかを求める位置の推定（GPS・SLAM・モーションキャプチャなど）が配る。Nav2 には、決まった地図の上で位置を推定する AMCL（particle filter による方法）と、位置を推定しながら地図を作る SLAM の既定として SLAM Toolbox が用意されている。
  • odom → base_link: odometry（Quickstart の章の 1 節）が配る。元になるのは、車輪の回転、IMU、LIDAR、レーダー、カメラによる推定（VIO）などである。odometry の役目は、途切れずなめらかに変わる座標系を与えることで、少しずつずれていく。そのずれを、位置の推定が map → odom を直して埋める。複数のセンサーを合わせて 1 つの odometry にするには、robot_localization がよく使われる。
  • base_link → センサー: ロボットの体に固定された関係なので、URDF（Quickstart の章の 8 節）で決める。

公式の文書は、LIDAR は必須ではないと強調している。カメラや深度センサーによる位置の推定でも、上の決まりの座標系をそろえさえすれば、Nav2 は使える。

動いていないロボットでは、odom → base_link は出発したときのままで、位置のずれはほぼ 0（高さの 0.010 m だけ）である。RViz で目標を与えてロボットを動かしてからもう一度実行すると、こちらの値が走った分だけ変わるはずである（想定。作成時は、ロボットを動かしてからは確かめていない）。

7. 環境の表し方

ロボットが周りをどう捉えるかを表すのが、環境の表し方である。いろいろなアルゴリズムとセンサーの情報を 1 つの空間に集め、controller・planner・behavior が安全に計算するために使う。Nav2 の今の表し方は、costmap である。costmap は、2 次元の格子のマスごとに、わからない・空いている・ふさがっている・ふさがった場所の近く（ふくらませた値）を表す値を持つ。planner は costmap を探して経路を計算し、controller は costmap を見て走れる動きを選ぶ。

costmap は、いくつもの layer（層）を重ねて作る。各 layer は pluginlib の plugin で、LIDAR・レーダー・ソナー・深度画像などの情報を costmap に取り込む。センサーの値を前もって処理してから layer に入れるかは、開発者が決める。カメラで障害物を見つけて追う layer や、決まりに沿って costmap を変える layer も作れる。

# T2
ros2 param get /global_costmap/global_costmap plugins

ros2 param get /local_costmap/local_costmap plugins

期待する結果

String values are: ['static_layer', 'obstacle_layer', 'inflation_layer']
String values are: ['voxel_layer', 'inflation_layer']

global costmap（planner が使う、地図の全体）は、地図を取り込む static_layer、センサーで見た障害物を取り込む obstacle_layer、障害物の周りに値を広げる inflation_layer の 3 つの layer でできている。local costmap（controller が使う、ロボットの周り）は、障害物を 3 次元のマスで扱う voxel_layer と inflation_layer の 2 つの layer である。layer の名前の付け方と中身は設定で決まり、Quickstart の既定の設定ではこうなっている。

costmap filter

地図の画像に印を付けて、場所に応じて振る舞いを変えたいことがある。たとえば、立ち入り禁止の場所や、速度を落とす場所である。この印を付けた地図を filter mask と呼ぶ。costmap filter は、filter mask を読んで、ロボットのいる場所に応じて costmap やロボットの振る舞いを変える layer の plugin である。立ち入り禁止・安全のための区域、速度の制限、倉庫で優先して通る道などに使える。

costmap のほかにも、地面の傾きを表す地図、3 次元の costmap（3 次元の経路の計算と衝突の判定が要る）、面の集まりで表す地図、機械学習で物を見つけて追う表し方などがある。

8. 製品に組み込むなら

  • 手で与えた目標を、製品の仕事の流れに置き換える。このページでは、目標を RViz から 1 つずつ手で与え、Nav2 の既定の設定（MPPI・NavFn・既定の behavior tree・AMCL）で動かした。製品では、目標を出す側と設定を、次のように考える。
  • waypoint following と配車の役割分担を決める。公式の文書は、複数のロボットを動かすときの 2 つの考え方を挙げている。1 つは「ロボットは単純、全体の配車が賢い」形で、配車の側がロボットの位置・電池・今の仕事を見て仕事を割り当てる。この場合は nav2_waypoint_follower をそのまま製品に使え、1 回の依頼を 1 つの仕事（倉庫での 1 回のピッキング、1 周の巡回など）として扱う。もう 1 つは「ロボットが賢い、配車は単純」形で、ロボットの上の仕事の流れ（途中で電池を確かめて充電台へ戻る、など）を、nav2_behavior_tree で自分の behavior tree として作る。どちらがよいかは、ロボットの仕事・環境・使えるクラウドの資源で決まる。
  • 自分のロボットでも、REP 105 の座標系をそろえる。位置の推定に LIDAR を使うかどうかにかかわらず、map → odom → base_link → センサーの木を、決まりどおりに配る。そうすれば、コミュニティの位置の推定・odometry・SLAM をそのまま使える。
  • 自分で作る node も lifecycle node にすることを考える。公式の文書は、使えるなら lifecycle node にするのがよいとしている。起動と終了の順番が決まる。Nav2 の nav2_util の LifecycleNode を使えば、bond も付く。
  • アルゴリズムは設定と plugin で替える。5 節のとおり、planner・controller などは設定で替えられ、足りなければ plugin やサーバーを足せる。Nav2 のリポジトリを分岐させて書き換える必要は無い。
