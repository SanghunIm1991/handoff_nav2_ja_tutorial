Local Installation：Nav2 の入れ方を知り、ソースからビルドする

環境構築と Quickstart の章では、言われたとおりにコマンドを打って、ROS 2 と Nav2 を入れた。動くものを先に見るためである。このページでは立ち止まって、そのとき入れた道具とパッケージが何のためのものだったのかを確かめる。

そのうえで、Nav2 をソースからビルドする。apt で入れた Nav2 は、出来上がったものを使うだけで、中身を変えられない。Nav2 のコードを読みながら動かしたり、直したり、自分の部品を足したりするには、ソースを手元に置いて自分で組み立てる必要がある。後の章（プラグインを作る章。準備中）で作るプラグインも、この組み立て方の上に乗る。

このページについて

  • Nav2 の公式の文書の Local Installation（jazzy 版の原稿、コミット b22554c）を基に、日本語で説明し直したもの。逐語の翻訳ではない。手順の意味の説明には、ROS 2 の公式の文書（出典に列挙）も使った。出典とライセンスはページの末尾にある。
  • ROS 2 Jazzy と Ubuntu 24.04（Windows の WSL2 を含む）を前提にする。環境構築と Quickstart の章を終えていることを前提にする。
  • 期待する結果の出どころ: 3 節〜5 節の表示は、どれも作成時の環境（navigation2 1.3.14 を apt で入れた環境）で実際に確かめたもの。ソースは、2026-11-22 に取得した jazzy ブランチの先頭である。
  • 4 節のビルドは、作成時の環境では、4-5 節の 1 つずつビルドする形で、途中で止まった回の続きから 1 時間半ほどかかった。かかる時間は PC によって大きく変わる。

0. 学習目標と完了条件

このページを終えると、次のことができる。

  1. これまでに入れた開発の道具（colcon・rosdep・vcstool）と Nav2 のパッケージが、それぞれ何のためにあるのかを説明できる。
  2. Nav2 の 2 つの入れ方（バイナリとソース）の違いを説明できる。
  3. Nav2 をソースからビルドし、ビルドした Nav2 を使うように環境を読み込める。

完了条件は、5 節の ros2 pkg prefix nav2_bringup が、apt で入れた場所ではなく、自分でビルドした場所を指すこと。

1. 全体像

公式の Local Installation は、2 つのものを入れる手順を並べている。Nav2 が依存するもの（ROS 2 と開発の道具）と、Nav2 そのものである。どちらにも、出来上がったものを apt で入れるバイナリの方法と、ソースのコードを手元で組み立てるソースの方法がある。このサイトでどこまで済んでいるかを、表にまとめる。

入れるものバイナリ（apt）ソース
ROS 2 と開発の道具環境構築の章の 4 節・5 節で済み。意味はこのページの 2 節このサイトでは扱わない（2 節のリンク）
Nav2Quickstart の章の 2 節で済み。意味はこのページの 3 節このページの 4 節・5 節

ソースからビルドした Nav2 は、apt で入れた Nav2 を消さずに、その上に重ねて使う。どちらが使われるかは、ターミナルでどの環境を読み込んだかで決まる（5 節）。

2. 依存するもの：ROS 2 と開発の道具

公式の原稿は、Nav2 を使う前に、ROS 2 と開発の道具 colcon・rosdep・vcstool を入れておくことを求めている。このサイトでは、環境構築の章の 5 節で、ROS 2 を ros-jazzy-desktop として、開発の道具を ros-dev-tools というまとまりとして apt で入れた。ros-dev-tools は、ROS 2 の公式の文書がソースから組み立てるときの道具として入れさせるものである。

  • colcon: workspace（ソースを置いてビルドするための決まった形のフォルダ。4 節で作る）の中の複数のパッケージを、依存の順に並べてまとめてビルドする。ROS 2 のパッケージは数が多く、互いに依存しているので、1 つずつ手でビルドする代わりにこれを使う。
  • rosdep: ソースのパッケージが必要とするほかのパッケージを調べて、apt でまとめて入れる。どこまでを rosdep に任せるかは 4-3 節で見る。
  • vcstool（コマンドは vcs）: 一覧のファイルに書かれた複数の Git のリポジトリを、まとめて取得する。ROS 2 そのものをソースから組み立てるときは、100 を超えるリポジトリを一覧のファイルから取得するのに使う。この章の手順で取得するのは 2 つのリポジトリで、公式の Nav2 の手順は git clone を使い、vcs は使わない。

公式の原稿は、ROS 2 そのものをソースから入れる方法も挙げているが、このサイトでは扱わない。必要なら、ROS 2 の公式の文書の Ubuntu (source) を参照する。

3. Nav2 をバイナリで入れる

Quickstart の章の 2 節で実行した apt install を、公式の原稿の形で書くと次のようになる。

# T1
sudo apt update
sudo apt install ros-$ROS_DISTRO-navigation2 ros-$ROS_DISTRO-nav2-bringup ros-$ROS_DISTRO-nav2-minimal-tb\*

このコマンドは、Quickstart で入れ済みなので、打たなくてよい。# T1 は「1 つめのターミナルで実行する」という印で、# から後はコメントなので打たなくてよい（この印は、この後のコマンドの箱でも同じ）。

$ROS_DISTRO は、ROS 2 の環境を読み込んだターミナルで、版の名前（ここでは jazzy）に置き換わる変数である。公式の原稿は、版を書き換えずに使えるよう、この形で書いている。Quickstart では jazzy と直接書いたので、中身は同じである。最後の \* は、Quickstart で '…' で囲んだのと同じく、* を bash に解釈させずにそのまま apt に渡す書き方である。この書き方なら $ROS_DISTRO は置き換わり、* はそのまま渡る（単引用符で全体を囲むと、$ROS_DISTRO も置き換わらない）。

入る 3 つのものは、次の役目を持つ。

  • ros-jazzy-navigation2: Nav2 の本体の部品（位置の推定・経路の計画・経路の追従など）をまとめて入れるためのパッケージ。
  • ros-jazzy-nav2-bringup: Nav2 をまとめて起動するための launch file と、既定の設定のファイル。Quickstart の tb3_simulation_launch.py もここにある。
  • ros-jazzy-nav2-minimal-tb*: シミュレーションで使う TurtleBot 3 と TurtleBot 4 の部品。

公式の原稿によると、Nav2 は、開発中の版（Rolling）を除く ROS 2 の各版に向けて、バイナリとして公開されている。apt で入れると、その版の最新の安定版が入る。入った場所を確かめる。

# T1
source /opt/ros/jazzy/setup.bash

ros2 pkg prefix nav2_bringup

期待する結果

/opt/ros/jazzy

ros2 pkg prefix は、指定したパッケージが入っている場所（の根元）を表示する。apt で入れた ROS 2 のパッケージは、どれも /opt/ros/jazzy の下にまとめて置かれている。

4. Nav2 をソースからビルドする

ここからが、まだ行っていない手順である。公式の原稿のコマンドを、意味の区切りごとに分けて実行する。すべて同じターミナル（T1）で、順に実行する。

4-1. workspace を作り、ソースを取得する

# T1
source /opt/ros/jazzy/setup.bash

NAV_DISTRO=${ROS_DISTRO/rolling/main}

mkdir -p ~/nav2_ws/src && cd ~/nav2_ws

git clone https://github.com/ros-navigation/navigation2.git --branch $NAV_DISTRO ./src/navigation2

git clone https://github.com/ros-navigation/nav2_minimal_turtlebot_simulation.git --branch $NAV_DISTRO ./src/nav2_minimal_turtlebot_simulation
  • NAV_DISTRO=${ROS_DISTRO/rolling/main}: $ROS_DISTRO の中の rolling を main に置き換えたものを、NAV_DISTRO に入れる bash の書き方。Nav2 のリポジトリは、ROS 2 の版と同じ名前のブランチ（jazzy など）を持ち、開発中の版 Rolling の分だけは main ブランチにある。Jazzy では置き換えが起きず、NAV_DISTRO は jazzy になる。
  • mkdir -p ~/nav2_ws/src: workspace のフォルダ ~/nav2_ws と、その中にソースを置く src を作る。ROS 2 の workspace は、src にソースを置き、workspace の直下で colcon を動かす決まった形をしている。
  • git clone … --branch $NAV_DISTRO: Nav2 の本体（navigation2）と、シミュレーションの TurtleBot（nav2_minimal_turtlebot_simulation）の jazzy ブランチを、src の下に取得する。ブランチは ROS 2 の版と必ず合わせる。公式の困りごとの手引きは、ある版のブランチを別の版では使えないと書いている。

期待する結果

（中略）
Resolving deltas: 100% (43997/43997), done.
Cloning into './src/nav2_minimal_turtlebot_simulation'...

2 つのリポジトリの取得が、どちらも done. で終わればよい。数は、リポジトリが更新されると変わる。取得した jazzy ブランチの先頭は、apt で入る版と同じとは限らない。作成時は、navigation2 が 1.3.14 より 5 コミット新しく、nav2_minimal_turtlebot_simulation は 1.0.3 より 1 コミット新しかった（apt では 1.0.1）。

4-2. rosdep を初めて使う前の準備

公式の Nav2 の原稿には無いが、rosdep を初めて使う PC では、先に次の 2 つが要る。ROS 2 の公式の文書の rosdep の説明が、初めて使うときの手順として書いているものである。環境構築の章で入れたのは rosdep のコマンドだけで、この準備はまだ済んでいない。

# T1
sudo rosdep init

rosdep update

rosdep は、パッケージが求めるものの名前（rosdep key。4-3 節で見る package.xml に書かれている）を、apt のパッケージの名前に当てはめる対応表を使う。sudo rosdep init は、その対応表をどこから取得するかを書いたファイルを作る（PC に 1 回だけ。管理者の権限が要る）。rosdep update は、対応表を取得して、ホームのフォルダに保存する（sudo は付けない）。

        rosdep update

rosdep update（抜粋）:

<ユーザー名> の部分は、Ubuntu のユーザー名になる。すでに準備を済ませた PC で sudo rosdep init を実行すると、ERROR: default sources list file already exists と出る。これは準備が済んでいるという意味なので、気にせず rosdep update に進む。

4-3. 足りない依存を入れる

# T1
rosdep install -r -y --from-paths ./src --ignore-src

各パッケージは、自分が必要とするものを package.xml（パッケージの名前・版・依存するものを書いたファイル）に書いている。rosdep install は、それを読んで、まだ入っていないものを apt で入れる。人が依存を覚えて入れるのではなく、各パッケージの package.xml に書かれたものを rosdep が apt の名前に置き換えて入れる、という分担である。

  • --from-paths ./src: src の下の package.xml をすべて読む。
  • --ignore-src: src の中にあるパッケージ（これから自分でビルドするもの）は、apt で入れない。
  • -y: apt の「続けますか」に、自動で「はい」と答える。
  • -r: 途中でエラーがあっても、残りを入れ続ける。

apt で入れた Nav2 があっても、ここで入るものがある。src には、apt の ros-jazzy-navigation2 に含まれないパッケージもあり、その依存は入っていないからである。また、package.xml には、テストにだけ使う依存（test_depend）も書かれている。作成時の環境では、そのテストの依存も、このコマンドで入った（期待する結果）。

最後に #All required rosdeps installed successfully が出ればよい。途中で sudo のパスワードを聞かれる。作成時の環境（Quickstart まで済んだ状態）では、上の 4 つが入った。各パッケージの package.xml を見ると、python3-transforms3d と ros-jazzy-tf-transformations は nav2_loopback_sim（ros-jazzy-navigation2 に含まれないパッケージ）が実行に使うもの、ros-jazzy-test-msgs と python3-zmq は test_depend に書かれたものだった。入るものは、PC にすでに入っているものによって変わり、すべてそろっていれば最後の 1 行だけが出る。

公式の原稿は、slam_toolbox が見つからないという rosdep のエラーは無視してよい、と書いている。作成時の環境では、Quickstart で slam_toolbox が入っていたためか、このエラーは出なかった。

4-4. ビルドする

メモリに余裕の無い PC（WSL に割り当てたメモリが少ない場合を含む）では、次のコマンドで PC が固まることがある。実行する前に 4-5 節を読み、心配なら最初から 4-5 節の形で実行する。

# T1
colcon build --symlink-install

colcon build は、workspace の直下で実行する。src の中のパッケージを依存の順に並べてビルドし、src の隣に 3 つのフォルダを作る。

  • build: ビルドの途中のファイル。
  • install: ビルドしたものの置き場所。5 節で使う。
  • log: ビルドのログ。失敗したときは、ここのパッケージごとのログを見る。

--symlink-install を付けると、install の中の Python のファイルや launch file などを、src のファイルへのリンク（symbolic link）にする。src のそれらのファイルを直せば、ビルドし直さずに直した内容が使われるので、試しながら直すときに速い。C++ のプログラムは、直したらビルドし直す必要がある。

期待する結果

（中略）
Starting >>> nav2_behavior_tree
Finished <<< nav2_behavior_tree [23min 11s]
（中略）

最後に Summary: 48 packages finished が出れば、すべてのパッケージのビルドが終わっている。パッケージの数は、ソースが更新されると変わる。Starting と Finished の間の時間は、パッケージによって大きく違う。作成時は nav2_behavior_tree（23 分）、nav2_costmap_2d（10 分）、nav2_route・nav2_mppi_controller（7 分）が長かった。この表示は、次の 4-5 節の 1 つずつビルドする形で取ったものなので、パッケージが 1 行ずつ順に並んでいる。既定の形では、複数のパッケージが同時に進み、[Processing: …] の行が挟まる。

4-5. PC が固まる・ビルドが止まるとき

ROS 2 の公式の colcon のチュートリアルは、CPU・メモリ・ディスクの読み書きの限られた PC では colcon build で画面とマウスが固まることがあるとして、パッケージを 1 つずつビルドする --executor sequential を挙げている。また、導入の困りごとの手引きは、メモリの限られた PC でコンパイラが異常終了するとき（internal compiler error）の対処として、コンパイルを 1 つずつにする MAKEFLAGS=-j1 を挙げている。

作成時の環境では、既定の形のビルドで画面が固まったり、表示の経過時間だけが増えてパーセントが進まなくなったりした。ビルドのログでは、1 つのパッケージの中で C++ のファイルを 5 つ以上同時にコンパイルし始めたところで止まっていたので、メモリを使い切ったと推定している（メモリが原因であることは確かめていない）。上の 2 つを両方付けると、同時に動くコンパイラは 1 つになる。

# T1
source /opt/ros/jazzy/setup.bash

cd ~/nav2_ws

MAKEFLAGS=-j1 colcon build --symlink-install --executor sequential

時間はかかるが、止まりにくくなる。作成時の環境では、既定の形で 1 回（裏でほかの作業も同時に動かしていた）PC ごと固まり、同時にビルドするパッケージの数だけを絞る --parallel-workers 2 でも止まった（colcon は、MAKEFLAGS が無いと、パッケージの中のコンパイルを CPU の数だけ並べるため。手元の colcon のコードで確かめた）。この形にして、最後まで通った。

ビルドが止まったら、Ctrl+C で止める。PC ごと固まって操作できないときは、PC を再起動するか、Windows の PowerShell で wsl --shutdown（環境構築の章の 2 節）を実行して WSL を止める。そのあと新しいターミナルで上のブロックを実行すれば、終わっていたパッケージはすぐに済み、続きから進む。

1 つずつの形は時間がかかる。ビルドする量そのものを減らすと、かかる時間を縮められる。ROS 2 の公式の文書は、次の 2 つを挙げている。

  • --packages-up-to <パッケージ名>: 指定したパッケージと、それが依存するパッケージだけをビルドし、workspace の全体はビルドしない（workspace のチュートリアル）。
  • --cmake-args -DBUILD_TESTING=0: CMake のパッケージのテストを組み立てない（colcon のチュートリアル）。4-4 節の全体のビルドには、nav2_system_tests などのテストも含まれていた。
# T1
MAKEFLAGS=-j1 colcon build --symlink-install --executor sequential --packages-up-to <パッケージ名> --cmake-args -DBUILD_TESTING=0

<パッケージ名> には、使いたいパッケージの名前（nav2_bringup など）を書く。ビルドしなかったパッケージは、5 節で見るとおり、apt で入れた /opt/ros/jazzy のものが使われる。自分でビルドした版と apt の版が混ざるので、どれをビルドしたかを意識しておく。重いパッケージ（nav2_behavior_tree など）が範囲に入れば、1 つのファイルのコンパイルに使うメモリは変わらないので、MAKEFLAGS の絞りは引き続き付けておく。作成時の環境では、この形は試していない。

5. ビルドした Nav2 を使う

ビルドが終わったら、新しいターミナル（T2）を開いて、workspace の環境を読み込む。ROS 2 の公式の文書は、ビルドしたのと同じターミナルで読み込むと込み入った問題が起きうるので、別のターミナルで読み込むよう勧めている。

# T2
source ~/nav2_ws/install/setup.bash

ros2 pkg prefix nav2_bringup

ros2 pkg prefix slam_toolbox

期待する結果

/home/<ユーザー名>/nav2_ws/install/nav2_bringup
/opt/ros/jazzy

1 行めの nav2_bringup が workspace の install を指していれば、ビルドした Nav2 が使われている。<ユーザー名> の部分は、Ubuntu のユーザー名になる。2 行めの slam_toolbox は workspace でビルドしていないので、apt で入れた /opt/ros/jazzy のものが使われる。

ROS 2 の公式の文書は、元からある環境（ここでは /opt/ros/jazzy）を underlay、その上に重ねる workspace を overlay と呼ぶ。overlay にあるパッケージは、underlay の同じ名前のパッケージより優先され、overlay に無いものは underlay のものが使われる（underlay の中身は変わらない）。workspace の install/setup.bash は、ビルドしたときの underlay もあわせて読み込むので、新しいターミナルではこの 1 行だけでよい。

この状態で、Quickstart の章の 3 節のコマンドのうち 2 行めの ros2 launch … だけを実行すると（1 行めの source /opt/ros/jazzy/setup.bash は打たなくてよい）、パッケージが上から探されるので、ビルドした Nav2 の launch file と node が使われる（作成時の環境では、起動しての確認はしていない）。apt で入れた Nav2 に戻すには、新しいターミナルで source /opt/ros/jazzy/setup.bash だけを読み込めばよい。ビルドした Nav2 を使うターミナルでは、毎回 source ~/nav2_ws/install/setup.bash を実行する。環境構築の章の 6 節で見たとおり、~/.bashrc に書き足すと、どちらの Nav2 を使っているかが見えにくくなる。

6. 製品に組み込むなら

  • Nav2 を変えずに使うなら、バイナリを使う。公式の原稿のとおり、バイナリはその版の最新の安定版で、ビルドの時間もかからない。ただし、Quickstart の章の 2 節で見たとおり、apt upgrade で版が変わる。製品では、どの版で試験したかを記録し、版を上げるときは試験し直す。
  • Nav2 を直す・部品を足すなら、ソースの workspace を overlay にする。直したいパッケージだけを workspace に置き、残りは underlay のバイナリを使う形もできる（ROS 2 の公式の文書は、少数のパッケージを直しながら試すときに overlay を使うことを勧めている）。
  • どのコミットをビルドしたかを記録する。同じ jazzy ブランチでも、取得した日によって中身が違う（4-1 節では、apt の版より新しいコミットだった）。製品に入れるものは、取得したコミットを決めて記録する。
  • ビルドする PC の資源を見積もる。4-5 節のとおり、Nav2 の全体のビルドは時間とメモリを使う。ロボットに載せる小さな PC でビルドするか、別の PC でビルドするかも、考えておく。
