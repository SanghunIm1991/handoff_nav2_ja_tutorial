Nav2 Behavior Trees：ロボットの動きの手順を木で読み、書き換える

Quickstart の章では、RViz で目標を与えると、ロボットが経路を計算し、その経路を追って目標に着いた。途中で道をふさがれれば、計算し直したり、その場で回ったりもする。製品に組み込もうとすると、この手順を変えたくなる場面が出てくる。障害物が消えるまで待ってから回り道を考えたい。エレベーターの前では扉が開くのを待ちたい。電池が減ったら、目標を捨てて充電に向かいたい。

Nav2 では、この「何をどの順に試すか」を、behavior tree（BT）という木の形の XML のファイルに書いている。プログラムを書き直さなくても、木のファイルを差し替えれば手順が変わる。このページでは、Nav2 が既定で使う木を読み、自分で書いた木に切り替えてロボットを走らせる。

このページについて

  • Nav2 の公式の文書の Nav2 Behavior Trees と、その下の Introduction To Nav2 Specific Nodes・Detailed Behavior Tree Walkthrough（jazzy 版の原稿、コミット b22554c）を基に、日本語で説明し直したもの。逐語の翻訳ではない。公式が用意しているほかの木の例は、次の用意されている木の章で見る。出典とライセンスはページの末尾にある。
  • ROS 2 Jazzy と Ubuntu 24.04（Windows の WSL2 を含む）を前提にする。Quickstart の章（シミュレーションの起動と初期位置の与え方）と、Navigation Concepts の章の 2 節（action）・4 節（behavior tree）を終えていることを前提にする。
  • 期待する結果の出どころ: 4 節の表示は、作成時の環境（apt で入れた Nav2 1.3.14）で、画面を出さずに確かめたもの（初期位置は、RViz の代わりにコマンドで与えた）。ログの時刻と目標の ID は、実行のたびに変わる。5 節で読む既定の木は、公式の原稿の XML と、Jazzy の apt の版（1.3.14）に入っているファイルとで、節と値がすべて同じであることを確かめた。2 節の RecoveryNode の回数の扱いと、4-4 節の error_code と ~ の扱いは、Nav2 のソース（jazzy ブランチ。1.3.14 の版とは、確かめた部分が同じであることを Git の差分で確かめた）で確かめた。

0. 学習目標と完了条件

このページを終えると、次のことができる。

  1. BT の節の 4 つの種類と、Nav2 に特有の主な節の役目を説明できる。
  2. Nav2 の既定の木を読んで、うまくいかないときに何をどの順に試すかを説明できる。
  3. 自分で書いた木に切り替えてロボットを走らせ、既定の木との振る舞いの違いをログから説明できる。

完了条件は、4 節で、簡単な木と既定の木のそれぞれで目標を送り、ログに回復の行（costmap を消す・その場で回る など）が出るか出ないかの違いを、5 節の木の形と結びつけて説明できること。

1. 全体像

Navigation Concepts の章の 4 節で見たとおり、BT は、やるべき仕事を木の形に並べて手順を組み立てる方法で、Nav2 は BehaviorTree.CPP というライブラリ（V4）を使っている。ここでは、木を読むのに要る決まりを 3 つ足す。

  • tick: 木は、根から順に節に「動け」という合図を送って進む。この合図を tick と呼ぶ。tick を受けた節は、SUCCESS（できた）・FAILURE（できなかった）・RUNNING（まだ途中）のどれかを親に返す。公式の原稿によると、Nav2 の木は 1 秒に 100 回 tick される。
  • 節の 4 つの種類: 実際の仕事をする action の節、条件を確かめるだけの condition の節（成り立てば SUCCESS、成り立たなければ FAILURE）、1 つの子を包んで tick の送り方を変える decorator の節、複数の子をどの順に tick するかを決める control の節である。木の葉は action か condition で、枝は decorator か control になる。
  • blackboard: 節どうしが値を受け渡すための共有の置き場。XML で {goal} や {path} のように波かっこで書いた名前は、blackboard の変数を指す。たとえば、経路を計算する節が {path} に書いた経路を、経路を追う節が {path} から読む。

言葉の注意: 公式の原稿は、初めのうちは言葉で混乱しやすいと注意している。BT の node（節）は、ROS 2 の node とはまったく別のものである。このサイトでは、BT の node を「節」と書いて区別する。また、BT の action の節は、ROS 2 の action とつながっているとは限らない（多くはつながっている）。

Nav2 では、bt_navigator が navigate_to_pose などの action で目標を受け取り（Navigation Concepts の章の 2 節）、木の XML を読み込んで tick を始める。木の中の action の節の多くは、planner・controller・behavior のサーバーを ROS 2 の action で呼ぶ。つまり、木が手順を決め、各サーバーが一つ一つの仕事をする、という分担になっている。

2. Nav2 に特有の節

BehaviorTree.CPP には、Sequence（子を順に、どれかが失敗するまで）や Fallback（子を順に、どれかが成功するまで）などの汎用の節がある。Nav2 は、それに加えて自分用の節を用意している。公式の原稿が主なものとして挙げる節は、次のとおりである（名前は XML に書く形にした）。すべての節の一覧は、nav2_behavior_tree の plugins のフォルダにある。

種類節役目
actionComputePathToPoseplanner のサーバーを action で呼び、目標までの経路を計算する
actionFollowPathcontroller のサーバーを action で呼び、経路を追う
actionSpin・Wait・BackUpbehavior のサーバーを action で呼び、その場で回る・待つ・下がる
actionClearEntireCostmapcostmap を消す。原稿の ClearCostmapService に当たる節で、action ではなく ROS 2 の service（依頼を送ると答えが 1 回返って終わる仕組み。action と違い、途中の経過は返らない）を呼ぶ
conditionGoalUpdated目標が新しくなったかを確かめる
conditionGoalReached・InitialPoseReceived・IsBatteryLow目標に着いたか・初期位置を受け取ったか・電池が減ったかを確かめる
decoratorRateController・DistanceController・SpeedController子を、決まった周期で・決まった距離を進むたびに・速さに応じた周期で tick する
decoratorGoalUpdater・SingleTrigger子の目標を差し替える・子を 1 回だけ tick する
controlPipelineSequence・RecoveryNode・RoundRobin下で説明する

3 つの control の節は、Nav2 の木の骨組みになっている。

  • PipelineSequence: 子を前から順に tick するが、汎用の Sequence と違い、後ろの子を tick するたびに、前の子も tick し直す（水が管を流れるように）。最後の子が SUCCESS を返すと、まだ動いている前の子を止めて、自分も SUCCESS を返す。どれかの子が FAILURE を返すと、すべての子を止めて FAILURE を返す。Nav2 では、「経路を追いながら、経路を計算し直す」に使う。
  • RecoveryNode: 子は 2 つだけで、1 つめが本来の仕事、2 つめが失敗したときの立て直しである。1 つめが FAILURE を返すと 2 つめを tick し、2 つめが成功したら 1 つめをやり直す。1 つめが成功すれば SUCCESS、2 つめが失敗するか、やり直しの回数（number_of_retries）を超えると FAILURE を返す。やり直しの回数は、親の節に止められると 0 に戻る（Nav2 のソースで確かめた）。そのため、一度失敗して親から外れた後、また tick されると、立て直しをもう一度試せる。
  • RoundRobin: 子を順番に tick し、どれかが SUCCESS を返したら自分も SUCCESS を返す。次に tick されたときは、前回成功した子の次の子から始める。すべての子が FAILURE なら FAILURE を返す。Nav2 では、回復のやり方を 1 回ごとに替えていくのに使う。

3. いちばん簡単な木

公式の原稿は、「とても簡単だが、ちゃんと動く」navigator の木として、次の XML を挙げている。4 節では、この木でロボットを走らせる。

4-2 節で、この内容を ~/nav2_bt_practice/simple_navigator.xml に書く。

<root main_tree_to_execute="MainTree">
  <BehaviorTree ID="MainTree">
    <PipelineSequence name="NavigateWithReplanning">
      <DistanceController distance="1.0">
        <ComputePathToPose goal="{goal}" path="{path}"/>
      </DistanceController>
      <FollowPath path="{path}"/>
    </PipelineSequence>
  </BehaviorTree>
</root>
  • <root> と <BehaviorTree ID="MainTree">: ファイルの中の木に名前を付け、どの木から始めるかを決める。
  • PipelineSequence: 2 節のとおり、経路の計算（1 つめの子）と経路の追従（2 つめの子）を、並べて tick し続ける。
  • DistanceController distance="1.0": ロボットが 1 m 進むたびに、子の ComputePathToPose を tick する。つまり、1 m ごとに経路を計算し直す。
  • ComputePathToPose goal="{goal}" path="{path}": blackboard の {goal}（bt_navigator が受け取った目標）までの経路を計算し、{path} に書く。
  • FollowPath path="{path}": {path} の経路を、controller のサーバーの既定のやり方で追う。

公式の原稿は、この木に無いものを並べている。うまくいかなかったときの回復の手順、失敗したときのやり直し、planner や controller のやり方の選択、状況に応じて設定を変える節、自動ドアやエレベーターとのやり取り、自分で作った節、ドッキングなどの別の動きの subtree などである。どれも、木を書き足せば Nav2 で使える。

4. 実習：自分の木で走らせる

目標を送る action の型 nav2_msgs/action/NavigateToPose は、目標の位置 pose のほかに、behavior_tree という欄を持っている。ここに木の XML のファイルの場所を書くと、その目標だけ、その木で走る。空のままなら、既定の木で走る。設定のファイルを変えずに木を試せるので、この実習ではこの欄を使う。

4-1. シミュレーションを起動し、初期位置を与える

Quickstart の章の 3 節のとおりに、1 つめのターミナル（T1）でシミュレーションを起動し、4 節のとおりに RViz の 2D Pose Estimate で初期位置を与える。ロボットのいる場所（Quickstart の章と同じ、x が -2.0・y が -0.5 のあたり）で、右向き（x が増える向き）に与える。T1 は、この後の木のログを見るのに使うので、閉じずにおく。

4-2. 木のファイルを作る

2 つめのターミナル（T2）を開き、3 節の XML をファイルに書く。# T2 は「2 つめのターミナルで実行する」という印で、# から後はコメントなので打たなくてよい。cat の行から最後の EOF の行までを、まとめて貼り付けて実行する。

# T2
mkdir -p ~/nav2_bt_practice

cat > ~/nav2_bt_practice/simple_navigator.xml <<'EOF'
<root main_tree_to_execute="MainTree">
  <BehaviorTree ID="MainTree">
    <PipelineSequence name="NavigateWithReplanning">
      <DistanceController distance="1.0">
        <ComputePathToPose goal="{goal}" path="{path}"/>
      </DistanceController>
      <FollowPath path="{path}"/>
    </PipelineSequence>
  </BehaviorTree>
</root>
EOF

<<'EOF' から EOF の行までが、ファイルに書かれる。'EOF' と引用符で囲むと、中に $ などがあっても、bash が書き換えずにそのまま書く（この XML には無いが、書き換えの心配が無い書き方として使う）。

4-3. 既定の木で走らせる

まず、behavior_tree の欄を空にして、既定の木で 1 m 先（x が -1.0）へ送る。

# T2
source /opt/ros/jazzy/setup.bash

ros2 action send_goal /navigate_to_pose nav2_msgs/action/NavigateToPose "{pose: {header: {frame_id: map}, pose: {position: {x: -1.0, y: -0.5, z: 0.0}, orientation: {w: 1.0}}}}"

ros2 action send_goal は、action の目標を 1 つ送り、結果が返るまで待つ。/navigate_to_pose が action の名前、nav2_msgs/action/NavigateToPose が型、最後の "{…}" が目標の中身（YAML の形）である。frame_id: map は、地図の座標で位置を書いたという意味で、orientation: {w: 1.0} は、地図の x が増える向き（4-1 節で与えた右向き）を表す。RViz の Nav2 Goal のボタンが内部でしていることを、コマンドで行っている。

4-4. 簡単な木で走らせる

次に、behavior_tree の欄に 4-2 節のファイルの場所を書いて、元の場所（x が -2.0）へ送る。ロボットは右を向いているので、目標は真後ろになる。

# T2
ros2 action send_goal /navigate_to_pose nav2_msgs/action/NavigateToPose "{pose: {header: {frame_id: map}, pose: {position: {x: -2.0, y: -0.5, z: 0.0}, orientation: {w: 1.0}}}, behavior_tree: '$HOME/nav2_bt_practice/simple_navigator.xml'}"

全体を "…" で囲んでいるので、中の '…' の中にある $HOME も、bash がホームのフォルダの場所に置き換える（'…' は、YAML でファイルの場所を 1 つの文字列として渡すための囲み）。bt_navigator は、受け取ったファイルの場所をそのまま開くので、~ と書いても置き換わらない（Nav2 のソースで確かめた）。そのため、$HOME で絶対パスにして渡す。

作成時の環境では、ロボットは約 0.9 m 動き、目標から約 0.3 m 離れた所で進めなくなった（止まった位置は、4-5 節の開始の位置から分かる。どう動いたかと、進めなくなった理由は確かめていない）。走り始めてから約 16 秒後に、controller のサーバーが Failed to make progress（決まった時間のうちに進めなかった）を出し、そのまま ABORTED（打ち切り）で終わった。この木には回復の手順が無いので、FollowPath の失敗がそのまま木の失敗になる。結果の error_code は、bt_navigator の設定（error_code_names）に並べた blackboard の名前（既定の木の compute_path_error_code など）に、木の節が書いた失敗の理由の番号から作られる（Nav2 のソースで確かめた）。この木の節はその番号を書かないので、0 のままになっている。

最初の 2 行の Warnings は、BehaviorTree.CPP の V4 が、<root> に BTCPP_format="4" を書くよう求めているという知らせで、木はそのまま読み込まれている。自分で木を書くときは、<root BTCPP_format="4" main_tree_to_execute="MainTree"> と書けば、この知らせは出ないはずである（確かめていない。5 節で読む既定の木も、この形で書かれている）。表示を抜粋した「中略」の中には、Warning: BehaviorTree ID [MainTree] in [<ファイルの場所>] replaces the one previously registered from [...] の行も出る。目標ごとに木を読み込み直して、前の木と入れ替えたという知らせで、問題は無い（4-5 節で既定の木に戻したときも出る）。

ロボットの位置や向きによっては、この木でも目標に着くことがある。その場合も、T1 のログに、次の 4-5 節で見る回復の行（costmap を消す・その場で回る）が出ないことを確かめる。

4-5. 同じ目標を既定の木で走らせる

最後に、4-4 節と同じ目標を、behavior_tree の欄を書かずに（既定の木で）送る。

# T2
ros2 action send_goal /navigate_to_pose nav2_msgs/action/NavigateToPose "{pose: {header: {frame_id: map}, pose: {position: {x: -2.0, y: -0.5, z: 0.0}, orientation: {w: 1.0}}}}"

作成時の環境では、4-4 節の後でロボットは (-2.00, -0.21) にいた。既定の木でも、最初は同じく Failed to make progress になった。けれども今度は打ち切らず、local costmap を消す → local と global の両方の costmap を消す → もう一度 local costmap を消す → その場で 90 度（1.57 ラジアン）回る、と立て直しを重ね、目標に着いた。この順番がどこから来るのかを、次の 5 節で木を読んで確かめる。どの回復で抜け出せるかは、そのときの位置や向きによって変わる。

読者の環境では、回復の行が 1 つも出ずに着くこともある（4-4 節で簡単な木が目標に着いたときや、既定の木がすぐに抜け出せたときなど）。その場合は、5 節の対応の表を、このページに載せた作成時のログで読めばよい。自分の環境でもう一度試すときは、4-5 節で目標に着いていれば、ロボットは元の場所にいるので、そのまま 4-3 節から繰り返す。RViz の 2D Pose Estimate は位置の推定を与え直すだけで、ロボットを動かさないので、ロボットを元の場所へ戻すのには使えない。着かなかったときは、Quickstart の章の 7 節のとおりに止めて、4-1 節から起動し直す。回復を 6 回試しても抜け出せなければ、既定の木でも ABORTED で終わる（5-1 節）。

実習が終わったら、Quickstart の章の 7 節のとおりに、T1 で Ctrl+C を押して止める。

5. 既定の木を読む

4-3 節と 4-5 節で使った既定の木は、navigate_to_pose_w_replanning_and_recovery.xml である。Navigation Concepts の章の 4 節で見たとおり、/opt/ros/jazzy/share/nav2_bt_navigator/behavior_trees/ にある（Local Installation の章でビルドした Nav2 で起動したときは、~/nav2_ws/install/nav2_bt_navigator/share/nav2_bt_navigator/behavior_trees/ の下にある）。less などで開くと、30 ほどの節が並んでいる。公式の原稿は、この木を 2 つの部分に分けて読んでいる。図 1 は、その骨組みである。

5-1. 根：航行と回復を行き来する

根の RecoveryNode（number_of_retries="6"）は、2 節で見たとおり、1 つめの子（航行）が失敗したら 2 つめの子（回復）を tick し、回復が成功したら航行をやり直す。これを 6 回まで繰り返す。木は、ほとんどの時間を航行の側で過ごし、航行の中で立て直せなかったときだけ回復の側へ移る。

5-2. 航行：経路を計算し直しながら追う

航行の PipelineSequence は、経路の計算（ComputePathToPose）が一度成功すると、経路の追従（FollowPath）を始め、その間も経路の計算を tick し続ける。そのため、ロボットが進むあいだも経路が計算し直される。経路の計算は RateController hz="1.0" に包まれていて、1 秒に 1 回だけ planner のサーバーを呼ぶ。公式の原稿は、木の tick（1 秒に 100 回）のたびに呼ぶと、planner のサーバーを無駄な依頼であふれさせてしまうためだと説明している。4-3 節で約 1 秒ごとに出た Passing new path to controller. は、これである。

経路の計算と経路の追従は、どちらも RecoveryNode（number_of_retries="1"）で包まれ、失敗したら、その場に合った立て直し（公式の原稿は contextual recovery と呼ぶ）を 1 回だけ試す。

  • 経路の計算が失敗したら: planner が使う global costmap を消す。
  • 経路の追従が失敗したら: controller が使う local costmap を消す。

どちらも、消す前に WouldAPlannerRecoveryHelp・WouldAControllerRecoveryHelp の condition の節で、失敗の理由の番号（error_code_id で blackboard に書かれる）を見て、消すことが役に立ちそうな失敗かを確かめている。4-5 節の最初の「local costmap を消す」は、この立て直しである。立て直しても再び失敗すると、航行の全体が FAILURE を返し、根が回復の側を tick する。

5-3. 回復：やり方を替えながら立て直す

回復の側は、システムの全体に関わる立て直しを受け持つ。

  1. Fallback の中の 2 つの condition の節で、航行の失敗が、回復で直りそうな種類のものかを確かめる。どちらも当てはまらなければ、回復の側は FAILURE を返し、木の全体が失敗で終わる。
  2. ReactiveFallback は、tick のたびに、まず 1 つめの子の GoalUpdated（新しい目標が来たか）を確かめる。新しい目標が来ていれば、回復を止めて SUCCESS を返し、すぐに航行へ戻る。公式の原稿は、これを「『この条件』が起きない限り、動作 A をする」という BT のよくある形として紹介している。
  3. 新しい目標が無ければ、RoundRobin が 4 つの回復のうち 1 つを試す。成功したら航行へ戻り、また航行が失敗して回復の側へ来たときは、次の回復を試す。順番は、① local と global の両方の costmap を消す、② その場で 90 度回る（Spin）、③ 5 秒待つ（Wait）、④ 30 cm 下がる（BackUp）である。

4-5 節のログを、この木に当てはめると次のようになる。

ログ木の中のどこか
1 回めの Failed to make progress → local costmap を消す航行の FollowPath の立て直し（1 回だけ）
2 回めの Failed to make progress → local と global の両方を消す航行が失敗し、回復の ① costmap を両方消す
3 回めの Failed to make progress → local costmap を消す航行に戻った後の、FollowPath の立て直し
4 回めの Failed to make progress → Running spin航行が再び失敗し、回復の ② Spin
Reached the goal!航行に戻り、FollowPath が成功

4-4 節の簡単な木では、1 回めの Failed to make progress で木の全体が失敗した。木に書かれた手順だけが行われる、ということが、2 つのログの違いに表れている。

6. 製品に組み込むなら

  • 既定の木から始めて、少しずつ変える。公式の原稿は、Nav2 に入っている木を、自分の用途に合わせて書き換えるか、自分の用途の木を作るときの手引きとして使うよう勧めている。回復の回数（number_of_retries）、経路を計算し直す周期（RateController の hz。代わりに DistanceController・SpeedController も使える）、回復のやり方の種類と順番は、木の XML を書き換えるだけで変えられる。公式の原稿は、周期を、用途と経路の計算の重さに合わせて決めるよう勧めている。
  • 製品の流れも木に入れられる。公式の原稿は、既定の木の全体を ReactiveFallback と IsBatteryLow で包めば、「電池が減らない限り目標へ向かい、減ったら充電へ向かう」木になる例を挙げている。エレベーターや自動ドアとのやり取りのように、Nav2 に無い仕事は、自分で節を作って足す（自分で作る節は、plugin の章〈準備中〉で扱う）。
  • 木のファイルも、製品の一部として管理する。木を変えるとロボットの振る舞いが変わるので、ソースと同じく版を管理し、変えたら試験し直す。4 節のように目標ごとに木を指定する方法は、試すには便利だが、製品では、既定の木を bt_navigator の設定（Navigation Concepts の章の 4 節で見た default_nav_to_pose_bt_xml など）で決めておくほうが、どの木で動いているかが分かりやすい。
  • 失敗の終わり方を決めておく。4-4 節のように、回復の手順の無い木は、すぐに ABORTED を返す。製品のアプリは、目標が打ち切られたときにどうするか（もう一度送る・人を呼ぶ など）を、木の回復の手順と合わせて決めておく。
