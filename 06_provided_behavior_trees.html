用意されている木：用途に合わせて behavior tree を選ぶ

Nav2 Behavior Trees の章では、Nav2 が既定で使う木を読み、木を差し替えると手順が変わることを確かめた。製品の要求は、倉庫で棚を順に回りたい、人の後について行きたい、ゴールの前に止まっているフォークリフトが去るまで待ちたい、とさまざまである。そのたびに木を一から書く必要は無い。Nav2 には、こうした用途に合わせた木の例が、すでにいくつも入っている。

このページでは、Nav2 が用意している木を 1 つずつ読み、既定の木とどこが違うのか、どんな場面で使うのかを見る。そのうち、複数の経由点を順に回る木は、実際に動かして確かめる。

このページについて

  • Nav2 の公式の文書の Nav2 Behavior Trees の下にある、木の例のページ（jazzy 版の原稿、コミット b22554c。個々のページは 1 節の表と末尾の出典にある）を基に、日本語で説明し直したもの。逐語の翻訳ではない。出典とライセンスはページの末尾にある。
  • ROS 2 Jazzy と Ubuntu 24.04（Windows の WSL2 を含む）を前提にする。Nav2 Behavior Trees の章（BT の読み方と、Nav2 に特有の節）を終えていることを前提にする。実習は、Quickstart の章のシミュレーションを使う。
  • 期待する結果の出どころ: 3 節の表示は、作成時の環境（apt で入れた Nav2 1.3.14）で、画面を出さずに確かめたもの（初期位置は、RViz の代わりにコマンドで与えた）。ログの時刻・目標の ID・feedback の数値は、実行のたびに変わる。このページで読む木の XML は、公式の原稿の XML と、Jazzy の apt の版（1.3.14）に入っているファイルとで、節と値がすべて同じであることを確かめた。4 節〜7 節の木は動かしておらず、振る舞いの説明は、木の形と公式の説明から読んだものである。

0. 学習目標と完了条件

このページを終えると、次のことができる。

  1. Nav2 が用意している木の中から、用途に合うものを選べる。
  2. それぞれの木が既定の木とどこで違うのかを、違いを生んでいる節の名前で説明できる。
  3. 複数の経由点を順に回る action に目標を送り、経由点が取り除かれていく様子を feedback で確かめられる。

完了条件は、3 節で 2 つの経由点を送り、feedback の number_of_poses_remaining が 2 から 1 に減る理由を、2 節の木の RemovePassedGoals の節と結びつけて説明できること。

同じフォルダには、公式の原稿が説明していない木も 6 つ入っている（navigate_w_replanning_time.xml・navigate_w_replanning_distance.xml・navigate_w_replanning_speed.xml・navigate_w_replanning_only_if_goal_is_updated.xml・navigate_w_replanning_only_if_path_becomes_invalid.xml・navigate_w_recovery_and_replanning_only_if_path_becomes_invalid.xml）。名前は、経路を計算し直すきっかけ（時間・距離・速さ・目標の更新・経路が無効になったとき）を表している。このページでは中身を扱わないが、XML を開けば、これまでに見た節の組み合わせで読める。

名前の決まり: どの木でも、経路を追う節は controller_id に FollowPath、経路を計算する節は planner_id に GridBased という名前を使う（実際には、…Selector の節を通して渡す）。これは、Quickstart の設定のファイル nav2_params.yaml で、controller のサーバーと planner のサーバーに登録したやり方の名前で、中身は MPPI と NavFn である。公式の原稿は、木の名前を DWB のようなアルゴリズムの名前ではなく、「経路を追う」のような役目の名前にしておくと、木やアプリを書く人がアルゴリズムの細部を気にせずに済む、と説明している。

2. Navigate Through Poses：経由点を順に通る

bt_navigator は、navigate_to_pose のほかに、navigate_through_poses という action も受け付けている（Navigation Concepts の章の 2 節の ros2 action list にも出ていた）。型は nav2_msgs/action/NavigateThroughPoses で、目標として 1 つの位置ではなく位置の並び（poses）を受け取る。並びの最後が最終の目標で、それより前が経由点である。この action の既定の木が、Navigate Through Poses の木である。

木の骨組みは、Nav2 Behavior Trees の章の 5 節で読んだ既定の木と同じで、根の RecoveryNode（6 回までやり直す）の下に、航行の PipelineSequence と回復の Sequence がある。回復の側（costmap を両方消す → 回る → 待つ → 下がる を順に試す）も同じである。違うのは、航行の側の経路の計算の部分で、XML では次のようになっている（抜粋）。

<RateController hz="0.333">
  <RecoveryNode number_of_retries="1" name="ComputePathThroughPoses">
    <ReactiveSequence>
      <RemovePassedGoals input_goals="{goals}" output_goals="{goals}"
        radius="0.7"/>
      <ComputePathThroughPoses goals="{goals}" path="{path}"
        planner_id="{selected_planner}"
        error_code_id="{compute_path_error_code}"/>
    </ReactiveSequence>
    <Sequence>
      <WouldAPlannerRecoveryHelp error_code="{compute_path_error_code}"/>
      <ClearEntireCostmap name="ClearGlobalCostmap-Context"
        service_name="global_costmap/clear_entirely_global_costmap"/>
    </Sequence>
  </RecoveryNode>
</RateController>
  • RateController hz="0.333": 経路の計算を、約 3 秒に 1 回にする（既定の木は 1 秒に 1 回）。
  • {goals}: bt_navigator が受け取った位置の並びが入る blackboard の変数。既定の木の {goal}（1 つの目標）に当たる。
  • RemovePassedGoals: ロボットが、並びの先頭（次に向かう経由点）から radius（0.7 m）以内に入ったら、その経由点を並びから取り除き、{goals} に書き戻す。公式の原稿は、通り過ぎた経由点を通る経路を、この先も計算し直し続けないためだと説明している。原稿の文章は「0.5 以内」と書いているが、XML の値は 0.7 である（0.5 は、この節の radius の既定値）。
  • ComputePathThroughPoses: 残った経由点を順に通って最後の目標へ着く経路を計算し、{path} に書く。既定の木の ComputePathToPose に当たる。
  • 2 つめの子の Sequence: 経路の計算が失敗したときの立て直しで、既定の木と同じく、役に立ちそうな失敗なら global costmap を消す。公式の原稿は、ここに別の planner のやり方を試す、といった立て直しを足せると書いている。

経路を追う部分（FollowPath と、失敗したら local costmap を消す立て直し）と、回復の側で新しい目標が来たら回復をやめる GoalUpdated も、既定の木と同じである。公式の原稿は、GoalUpdated があるので、回復の途中でも新しい目標にすぐ応じられると説明している。

やり方を外から切り替える節: この木の航行の先頭には、既定の木と同じく ControllerSelector・PlannerSelector があり、controller_selector・planner_selector の topic に名前を送ると、使う controller と planner のやり方を外から切り替えられる（送らなければ FollowPath・GridBased）。公式の原稿は、外から切り替えるより、condition の節で場面を見分けて、場面ごとに違うやり方を使う subtree を木の中に書くほうがよい、と勧めている。そのうえで、外のアプリから設定を変えたい利用者が多いことも認めている。なお、原稿の文章は「この木は選ぶ節を使っていない」と書いているが、XML には上の 2 つが入っている。

3. 実習：経由点を順に回る

2 つの経由点を navigate_through_poses に送り、経由点が取り除かれていく様子を feedback（action の途中の経過。Navigation Concepts の章の 2 節）で見る。

3-1. シミュレーションを起動し、初期位置を与える

Quickstart の章の 3 節のとおりに、1 つめのターミナル（T1）でシミュレーションを起動し、4 節のとおりに RViz の 2D Pose Estimate で初期位置を与える。ロボットのいる場所（x が -2.0・y が -0.5 のあたり）で、右向き（x が増える向き）に与える。T1 は、この後のログを見るのに使うので、閉じずにおく。

3-2. 2 つの経由点を送る

2 つめのターミナル（T2）を開いて、次を実行する。# T2 は「2 つめのターミナルで実行する」という印で、# から後はコメントなので打たなくてよい。1 つめの位置 (-0.5, -0.5) が経由点、2 つめの位置 (0.5, -0.5) が最後の目標で、どちらもロボットの前方（右）にある。

# T2
source /opt/ros/jazzy/setup.bash

ros2 action send_goal /navigate_through_poses nav2_msgs/action/NavigateThroughPoses "{poses: [{header: {frame_id: map}, pose: {position: {x: -0.5, y: -0.5, z: 0.0}, orientation: {w: 1.0}}}, {header: {frame_id: map}, pose: {position: {x: 0.5, y: -0.5, z: 0.0}, orientation: {w: 1.0}}}]}" --feedback

Nav2 Behavior Trees の章の 4-3 節の send_goal と同じ形で、目標の中身の poses: […] に、位置を 2 つ並べている。--feedback を付けると、結果のほかに、途中の経過も表示する。

number_of_poses_remaining は、まだ残っている位置の数である。最初は 2 で、走り始めてから約 3 秒の feedback で 1 に減った。そのときロボットは (-0.96, -0.57) にいて、1 つめの経由点 (-0.5, -0.5) まで約 0.47 m だった。RemovePassedGoals が、経由点の 0.7 m 以内に入ったロボットを見て、経由点を並びから取り除いたのである。distance_remaining（最後の目標までの残りの道のり。最初の feedback ではまだ経路が無いので 0）は、このとき約 1.5 m だった。

経由点から 0.7 m 以内に入ったのは、もう少し前だったはずである。それでも約 3 秒の時点で減ったのは、RemovePassedGoals が RateController hz="0.333" の下にあり、約 3 秒ごとの経路の計算のときにしか tick されないためと読める（木の形からの読みで、Nav2 のソースでは確かめていない）。最後の目標は取り除かれず、number_of_poses_remaining は終わりまで 1 のままだった。T1 の through 2 poses は、2 つの位置を受け取ったという表示である。作成時の環境では、目標を受け付けてから約 6 秒で SUCCEEDED になり、回復は 1 回も起きなかった（feedback の number_of_recoveries が 0 のまま）。

経由点の位置によっては、経由点の近くを通らない経路になり、経由点が取り除かれないまま最後の目標に着くこともある。その場合も、number_of_poses_remaining の数と、ロボットの位置（current_pose）とを見比べれば、何が起きたかを読める。

実習が終わったら、Quickstart の章の 7 節のとおりに、T1 で Ctrl+C を押して止める。

4. Navigate To Pose and Pause Near Goal-Obstacle：ゴールの前で待つ

目標の近くに、一時的な障害物（フォークリフト・人など）が止まっていることがある。既定の木は、経路を計算し直して回り道をする。けれども、障害物がすぐに去るなら、回り道より少し待つほうが早く着く。この木は、そのための木で、公式の原稿は、仕事の 1 回にかかる時間（cycle time）を縮めたい現場に向けた例として紹介している。

既定の木との違いは、経路を追う部分にある。既定の木では FollowPath を包む RecoveryNode がそのまま航行の 2 つめの子だったが、この木では、その前に見張りの枝が入っている（図 1）。経路の計算の周期（1 秒に 1 回）と回復の側は、既定の木と同じである。

  • ReactiveSequence（XML の名前は MonitorAndFollowPath）: 子を順に tick するが、tick のたびに先頭の子から確かめ直す（Nav2 Behavior Trees の章の 5-3 節の ReactiveFallback と同じく、条件を毎回見張る形）。そのため、左の見張りの子が SUCCESS を返さない限り、右の FollowPath は tick されない。公式の原稿は、この見張りの枝を、ロボットに見張らせたいことを利用者が書き足すための場所として作ったと説明している。
  • PathLongerOnApproach（decorator）: 新しく計算した経路を、前の経路と比べる。目標まで prox_len（3.0 m）以内に近づいたところで、新しい経路が前の経路の length_factor（2.0）倍より長くなっていたら、子を tick する。そうでなければ子を tick せずに SUCCESS を返し、右の FollowPath がそのまま進む。
  • 子の SequenceWithMemory: CancelControl で controller のサーバーの仕事を取り消してロボットを止め、Wait で 5 秒待つ。SequenceWithMemory は、前回どの子まで終えたかを覚えていて、次の tick では続きの子から始める Sequence である。

公式の原稿は、結末を 2 つに分けて説明している。

  • 待つ間に障害物が去った: planner が短い経路を計算し直すので、PathLongerOnApproach が SUCCESS を返し、FollowPath が短い経路で進む。
  • 障害物が去らない: 待ち時間が過ぎると、長い経路（回り道）で目標へ向かう。

公式のページには、この 2 つの結末の動画と、木の全体の図がある（このサイトには転載していない）。待ち時間（Wait の wait_duration）・「目標の手前」の距離・「長くなった」の倍率は、XML の値を書き換えれば、現場に合わせて変えられる。

5. Navigate To Pose With Consistent Replanning And If Path Becomes Invalid：要るときだけ計算し直す

1 つの目標へ向かう木で、公式の原稿は、既定の木をずっと成熟させたものと位置づけている。既定の木は、経路を 1 秒に 1 回、いつも計算し直していた。この木は、経路の計算の部分を次の形にして、計算し直すのを要るときだけにしている（抜粋。RateController と立て直しの RecoveryNode は略した）。

<Fallback>
  <ReactiveSequence>
    <Inverter>
      <PathExpiringTimer seconds="10" path="{path}"/>
    </Inverter>
    <Inverter>
      <GlobalUpdatedGoal/>
    </Inverter>
    <IsPathValid path="{path}"/>
  </ReactiveSequence>
  <ComputePathToPose goal="{goal}" path="{path}"
    planner_id="{selected_planner}"
    error_code_id="{compute_path_error_code}"/>
</Fallback>

Fallback は、子を順に、どれかが成功するまで tick する（Nav2 Behavior Trees の章の 2 節）。1 つめの子の ReactiveSequence が成功すれば、2 つめの子の ComputePathToPose は tick されず、今の経路を使い続ける。1 つめの子が成功するのは、次の 3 つがすべて成り立つときである。

  • PathExpiringTimer は、経路が新しくなってから seconds（10 秒）たつと SUCCESS を返す condition の節である。Inverter（子の SUCCESS と FAILURE を入れ替える decorator）で包んであるので、「経路が新しくなってから 10 秒たっていない」が条件になる。
  • GlobalUpdatedGoal は、目標が変わったら SUCCESS を返す。Inverter で包んで「目標が変わっていない」が条件になる。Nav2 Behavior Trees の章で見た GoalUpdated との違いは、公式の説明では、tick をまたいで今の目標を覚えておき、木のどこから見ても目標の変化に気づける点である。
  • IsPathValid は、今の経路の上に障害物が無ければ SUCCESS を返す。

裏返すと、経路が無効になった・目標が変わった・10 秒たったのどれかが起きたときだけ、経路を計算し直す。この確かめは RateController hz="2.0" の下にあり、1 秒に 2 回行われる。経路を追う部分と回復の側は、既定の木と同じである。

経路をいつも計算し直すと、計算のたびに経路が少しずつ変わり、ロボットの動きが揺れることがある。この木は、経路が使えるうちは同じ経路を使い続け、それでも 10 秒ごとには計算し直して、新しく見えてきた近道も拾う。どちらを選ぶかは、planner の計算の重さと、動きの安定のどちらを重く見るかによる。

6. Follow Dynamic Point：動く点の後について行く

動く点（人・別のロボット・仮想の目印など）の後について行く木である。公式の原稿によると、条件は、ついて行きたい位置を、GoalUpdater の節が見ている topic に送り続けることだけである。木の全体は、次のとおり短い。

<PipelineSequence name="NavigateWithReplanning">
  <ControllerSelector … />
  <PlannerSelector … />
  <RateController hz="1.0">
    <Sequence>
      <GoalUpdater input_goal="{goal}" output_goal="{updated_goal}">
        <ComputePathToPose goal="{updated_goal}" path="{path}"
          planner_id="{selected_planner}"
          error_code_id="{compute_path_error_code}"/>
      </GoalUpdater>
      <TruncatePath distance="1.0"
        input_path="{path}" output_path="{truncated_path}"/>
    </Sequence>
  </RateController>
  <KeepRunningUntilFailure>
    <FollowPath path="{truncated_path}" controller_id="{selected_controller}"
      error_code_id="{follow_path_error_code}"/>
  </KeepRunningUntilFailure>
</PipelineSequence>
  • GoalUpdater（decorator）: topic /goal_update（bt_navigator の parameter goal_updater_topic の既定値）で新しい位置を受け取っていたら、それを {updated_goal} に書き、子の ComputePathToPose の目標にする。受け取っていなければ、元の目標（{goal}）のままにする。経路の計算は 1 秒に 1 回で、そのたびに最新の位置を目標にする。
  • TruncatePath: 計算した経路の終わりから、目標までの距離が distance（1.0 m）より近い部分を切り落とす。ロボットは、止まったときも、ついて行く相手から少なくとも 1 m 離れていられる。公式の原稿は、相手のいる場所（costmap では障害物として埋まっていることが多い）へ向かって経路を計算するときの、不自然な動きを和らげる効果も挙げている。
  • KeepRunningUntilFailure（decorator）: 子が SUCCESS を返しても、RUNNING に置き換えて、子を tick し続ける。経路の終わりに着いても木は終わらない。

そのため、この木は、目標を取り消されるか、新しい目標で置き換えられるまで動き続ける。回復の部分も無いので、経路の計算や追従が失敗すると、そのまま木の全体が失敗する。製品で使うなら、ついて行く相手を見失ったときにどうするかを、木の外（アプリ）で決めておく必要がある。

この木を実際に動かす実習は、公式の Tutorials の Dynamic Object Following にあり、このサイトでは Tutorials を差し込む章（準備中）で扱う予定である。

7. Odometry Calibration：正方形を走って odometry を測る

ロボットに、1 辺 2 m の正方形を左回り（反時計回り）に 3 周させる木である。Repeat num_cycles="3" の下の Sequence に、DriveOnHeading（今の向きのまま、dist_to_travel の 2.0 m を speed の 0.2 m/s で進む）と Spin（spin_dist の 1.570796 ラジアン、つまり 90 度回る）の組が 4 つ並んでいる。どちらも behavior のサーバーの仕事で、経路の計算も目標も使わない。Spin の is_recovery="false" は、回復としてではなく、ふつうの仕事として回ることを表す。

公式の原稿は、これを odometry（車輪の回転などから推定した自分の動き）の正確さを測る簡単な実験と位置づけ、odometry に関わる parameter を調整するたびに繰り返して、質を上げるのに使えると説明している。たとえば、走り終えた後に、ロボットが実際に出発点へ戻ったかと、odometry が示す位置とを比べる。

この木は、ロボットの周りに 2 m 四方より広い空きが要る。Quickstart の世界は、初期位置の近くに柱が並んでいるので、そのままでは柱に当たりうる（作成時は試していない）。試すなら、空いた場所の世界を用意するか、実機を広い場所に置いて使う。Nav2 Behavior Trees の章の 4-4 節と同じく、navigate_to_pose の目標の behavior_tree の欄にこの木のファイルの場所を書けば走らせられるはずである（確かめていない）。木は目標の位置を使わないので、ロボットは送った位置へは向かわず、その場から正方形を描き始める。

8. 製品に組み込むなら

  • 用意された木を部品として使う。このページの木は、どれも既定の木の一部を差し替えたものだった。製品の木を作るときも、近い木を選び、違いの部分（見張りの枝、経路を計算し直す条件、目標の差し替えなど）を組み合わせる。たとえば、ゴールの前で待つ見張りの枝を、経由点を回る木に入れることもできる。組み合わせた木は、このページの 3 節や Nav2 Behavior Trees の章の 4 節のように、behavior_tree の欄で試してから既定にする。
  • 既定の木を設定で決める。2 つの action の既定の木は、bt_navigator の parameter の default_nav_to_pose_bt_xml・default_nav_through_poses_bt_xml で決める（空なら、このページで見た nav2_bt_navigator の木を使う）。どの木で動いているかが設定のファイルで分かるように、製品ではこちらを使う。
  • 経由点の回り方を選ぶ。navigate_through_poses は、経由点を通る経路を計算して追う action で、この木には経由点ごとに仕事を挟む節は無い。経由点ごとに止まって仕事（写真を撮る・荷を受け取るなど）をしたいなら、Navigation Concepts の章の 5 節の waypoint following が、各地点の仕事を plugin で差し込める仕組みになっている。
  • 終わらない木の止め方を決める。Follow Dynamic Point のように取り消すまで終わらない木を使うなら、アプリの側で、いつ取り消すか・相手を見失ったらどうするかを決めておく。
  • 使う版の木を確かめる。Route Graph の木のように、公式の文書にあっても、使っている版に入っていない木や節がある。木を採り入れる前に、使う版の behavior_trees/ と節の一覧（nav2_tree_nodes.xml）にあるかを確かめる。
